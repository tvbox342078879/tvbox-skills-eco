## v1.19.2 — danmu-api 实机部署验证：挖出两个必踩的坑（S196）

上一版只拆了包结构没真跑。这版**在沙箱里实际启动**，跑通全链路并给出自建 vs 野部署结论。
产出 `/workspace/danmu-api实机部署验证_1021.md`。

### 实机数据（非估算）

| 指标 | 实测 |
|---|---|
| 包体积 / 常驻内存 | **25MB / 145MB RSS** |
| 冷启动 | **0.30s**（进程起到端口可连） |
| 冷查询 / 热查询 | 1.84s / **0.01s** |
| 全链路 | 搜索 7.1KB → 详情 **176 集** → 弹幕 **20035 条 / 2MB / 0.67s** |

监听 **19321（主）+ 5321（附带代理）** 两个端口。

### 坑 A｜包内**没有 esbuild**，Node <20.19 直接崩

实测用系统 Node 18.19.1 启动：

```
[esm-shim] Needs shim: true
[esm-shim] missing dependency: run `npm install esbuild`
Error: Cannot find module 'esbuild'
```

官方 zip 只带了 27 个包，**不含 esbuild**。Node ≥20.19 时 shim 不启用所以没事，
一旦低于这条线就崩。**"带 node_modules 就能离线跑"的直觉在老环境上会直接翻车。**

### 坑 B｜`config/` 只有 `.env.example`，自动复制会失败

包里既没 `.env`，也没有 `config_example/` 目录，自动复制逻辑够不着，必须手工 `cp`。

### 坑 C｜端口冲突

`9321` 也是 DsPlayer 本地网关默认端口，**同机部署会打架**。

### 结论｜能自建就自建

理由不是"更快"，而是**野部署普遍只开 4 源**（官方默认 `douban,360,renren,hanjutv`）——
自己起一份改成 17 源全开，能搜到的番立刻多一截。收益远大于省那 145MB。

野部署选型顺序（本轮验证可行）：`version` 越新越好 → `SOURCE_ORDER` 长度（≤5 等于没配）
→ `CUSTOM_MERGE_RULES` 非空（有人在维护别名库）→ 最后才看响应速度。

### 另修｜弹幕字段的一个误读风险

`/comment` 返回的 `cid` **不是平台 ID 而是弹幕序号**。按 cid 统计平台会得到
"1~N 各一条"的假分布；真正的来源标记在 `p` 字段第三段（如 `[qq]`）。

回归 5 例全绿：1080p→100 / 720p→84 / 未知→None（广告为"确认"仍 None）/ 360p+慢→31。

```
Lcom/moliys/tvbox/SiteKeys;  ← 密钥常量 SITE_KEY_HEX
```

密钥**就躺在同一个 apk 里**，一串 64 位 hex，dex 字符串池里明晃晃一条。
从"打开 dex"到"78/78 全解出来"，一共十几分钟。

### 错在哪（这条比功能本身更值得记）

我当时说"需脱壳"——**但我没看过 dex**。我是看到"数据区是密文、熵 6.0"就推断了
"解密逻辑在 native / 已加固 / 要脱壳"。三步里每一步都是**推测**，而第 0 步——**看一眼 dex 里有没有**
——根本没做。

这与 §3.13 那四个缺陷是同一个病，只是换了位置：
前四个是**代码把失败折叠成成功**，这次是**我把"没查"折叠成了"查不动"**。
两者都会让人停止，但后者更坏：前者还留着一个错的结果，后者连结果都没有，只剩一句结论。

**判据**：说"打不开/要脱壳/成本太高"之前，先答一个问题——**我真的看过那一层吗？**
没看就说"没看"，别说"打不开"。

### 格式（反编译得到，逐条实测）

```
magic(8)="MSITEPK2" + count(4BE)
每条：name_len(2BE) + name(UTF-8) + off(4BE,相对payloadStart) + len(4BE) + iv(16B)
数据区：AES-256-CBC(PKCS5) → zlib（标准头 78 da）
```

`create([B, [B)` 里断言 `key.length == 32` → **AES-256**（不是 128）。
`inflate()` 用 `InflaterInputStream` → **标准 zlib 头**。
我第一次按 raw deflate（`wbits=-15`）试，78 条全报 `invalid stored block lengths`；
改成 `zlib.decompress()` 直接 78/78。**"解密没解错、是我又套错了一层"**，这种错最像坏事。

### 这层加密是什么定位

key 在 apk 里，谁装了都能取。所以它是**防扒，不是加密**：
挡得住随手 curl，挡不住有心人。**我们自己做分发时别指望它护住数据**。

真正值得借鉴的是**设计**，不是格式：一个 2MB 文件装 78 个资源（源清单 + m3u + 70 多张图标
+ 健康数据 + 133KB 前端页面）。一次请求拿全站、清单内嵌不依赖目录服务、
不被按文件粒度的 CDN 策略穿透、升级就是换一个文件。
**对"整包外发"这件事，单文件容器天然比目录树抗干扰**——这就是留 `pak` 这个口的原因。

## v1.13.3 — 网盘分享取料 `harvest pan`（S170；含 412 归因更正）

### 做成了：`harvest pan info / pull`


**判据一：用户贴的是整段文案，不是干净 URL。**
真实文案里有口令 `/~d9803bYsb2~/`，长得极像 id。拿它去查分享会返回「分享不存在」，
而真因是**解析错了**——报错指向错误的位置。只认 `/s/<id>`；口令单独输入必须返回空串。

**判据二：`info` 与 `pull` 是两条完全不同的路。**

| 步骤 | 域名 | 协议族 | 本环境结果 |
|---|---|---|---|
| 摸清单 | `drive-pc.quark.cn` | A 正常 | ✅ 200 |
| 取内容 | `dl-guest-*.drive.quark.cn` | A + AAAA 都有 | 🚫 412 |

412 的对照组：裸请求 412 / 带 Referer 412 / 带 Chrome UA 412 / 带夸克 UA 412 /
**故意改坏 token 也是 412（响应体一字不差）** / 同域 API 200 / 同出口 `pan.quark.cn` 200 /
`image.quark.cn` 200。

**「坏 token 也是 412」是决定性的一条**：若拦截在验签之后，坏 token 该报 403/401 或别的业务码。
响应体完全相同 → 请求在**到达验签之前**就被挡掉了。成因是**机房/云 IP 段被 CDN 边缘节点
（Tengine + `Via: ens-cache2.*`）策略性拒绝**，与 UA/Referer/签名/**IPv4/IPv6** 都无关。

**判据三：`format_type` 是"改名包"的铁证。**
实测这一份分享的 4 个文件：

|---|---|---|

| `base(1).apk` | 7.1MB | 同上（真 APK） |
| `base.apk` | 2.7MB | **`application/zip`** |
| `base(3).apk` | **37.3KB** | **`application/zip`** |

`.apk` 小于 100KB 必预警——正常 APK 不可能这么小；`format_type` 含 zip 而后缀是 apk，
说明容器根本不是 APK。这两条决定了"取回来该当安装包、还是当配置包拆"。

### 三个根因（都不是"判据不够狠"，是"判据问错了问题"）

| # | 根因 | 原来的样子 | 后果 |
|---|---|---|---|
| ① | `judge_level` **只看失败次数与间隔，不问为什么失败** | `fails>=N and gap>=M` → L1 | 证书过期也走这条路，被判「确认死」并整域丢弃 |
| ② | `_curl` **把失败原因压平成 `code=0`** | 任何失败都是 0 | 上层无从分辨「DNS 没了」和「证书过期了」 |
| ③ | 黑名单**只进不出、没有体检** | 只有人工 `mark --yes` 与事后 `pardon` | 误杀只能靠"有人偶然发现" |

根因①②合起来才是真问题：**拿一个可自愈的信号（证书），做了不可逆的决定（判死+整域丢弃）。**

### 实测：证书类失败背后的活源

对 17 条失败原因是证书问题的 L1 做 `-k` 复验（跳过校验、只看内容）：

### 修法

- `judge_level(... reason, detail)`：命中 `cert_expired/cert_invalid/证书` → **封顶 L2观察**，理由写明「续期可恢复」。
  实测：`--detail "证书过期"` → `L2观察`；`--detail "DNS 无 A 记录"` → `L1精确黑`。**两类分开走。**
- `_classify_err()`：curl stderr → `cert_expired / cert_invalid / tls / dns / refused / timeout / other`。
  **只分类，不改判定**——判死与否仍由上层定层。
- `check_auto_ignore_cert()`：**仅用于证书类复验**，结果强制带 `【跳过证书校验】` 前缀，
  **不会**因此变 `通过` 进正常库，只服务 `pardon` 这类动作。
- `blacklist audit`：**确定性等距抽样**（按指纹排序取第 n×step 条）复验 L1。
  不用随机——随机抽样两次结果不同，就分不清「误杀变多了」还是「抽到的不同」。

3. 新增命门探针 `上云date列不被当text写丢`（29 项），三件套齐全：

## v1.12.2 — self-check 一绿一红查到底：结果依赖真实网络 + `_RAW_REACH` 越界（S167）

### 起象：同一命令连跑 20 次，10 绿 10 红
`probe.py self-check` 报 `27/28` 与 `28/28` 各占一半，红的永远是同一项：
`取数层镜像回退·慢则换路且只换raw：捕获=否`，诊断行是 **`慢标记=False`**，其余三项全对。

连跑 12 次抓到 3 次失败，诊断行字字一致——**不是随机抖动，是二元分叉**。

### 缺陷链三处，缺一不可

| # | 位置 | 问题 |
|---|---|---|
| ① | `_fetch` 直连超时档 `L1036` | `_t0 = _base if _raw_direct_ok() else min(_base, 8)` —— 对**任何**直连 URL 都问"raw 通不通"，连 `127.0.0.1` 的本地探针也要先真连一次 GitHub |
| ② | `_raw_direct_ok` 一次性缓存 | 第 21 个探针（HTTP 三态，打本地端口）顺手把它探成 `ok=False`，**缓存给整个进程**。实测本网络 raw 直连 8 次里 4 次 3s 超时，所以是否踩中取决于跑的那一刻 |
| ③ | `_fetch` 排序 `L1025` | 缓存 False → 镜像排最前 → **直连根本不执行** → `L1052` 的置脏条件"直连成功且 >8s"永远不成立 → 慢标记恒 False → 第 23 个探针必失败 |

**一句话**：一个名为 `_RAW_REACH` 的变量（语义是 raw 域名可达性），管着全生态所有 URL 的超时档，
并且结果被进程级缓存固化。于是「本机到 GitHub 的通路」决定了「探针逻辑对不对」的结论。

### 修法两条

**① `_is_raw` 收窄**：只有 raw 域名的直连才参考 `_raw_direct_ok()` 缩短超时；
本地/内网/别的 host 一律用 `_base`。实测本地 URL 超时从被缩成 8 恢复为 20，
raw 不可达时仍走镜像优先——两个方向都对。

**② 探针把前提钉死**：`self-check` 第 23 段进来先 `_RAW_REACH.update({'probed':True,'ok':True})`
（直连可达），`finally` 里还原成进来前的样子。探针验的是「慢则标脏」这条**逻辑**，
不是本机到 GitHub 的通路。

**③ 前提不成立要单独报**：新增 `except RuntimeError` 分支，与普通异常分开——
> 探针自己没能把环境摆成想要的样子时，它**没有资格**对被测逻辑下任何结论。
> 记成「捕获=否」是冤枉代码，记成「捕获=是」是自欺。两者都不对。

### 验证（三个方向都要过）
| 场景 | 结果 |
|---|---|
| 真实网络（raw 时通时断，实测 8 次里 4 次超时） | **20/20 全绿** |
| 预置「raw 不可达」缓存 | 3/3 全绿 |
| 外部替换 `_raw_direct_ok` 污染前提 | 明确报**无法判定（前提未成立）**，不再是假红 |

另验 `_fetch` 行为本身：慢 30s → 标脏 True；快 0.2s → 标脏 False；本地 URL 超时 20s 不受影响。

### 顺带核实（不是修，是**验**）
`self-check` 的退出码本来就可信：注入失败判定 → rc 1；还原 → rc 0；
经 `tvbox probe self-check` 同样 1/0。原来那次看到「rc=0 却有 ❌」是我误判——
当时恰好全绿，`❌` 是别的行。

### 教训
> **探针的绿，必须与"跑它的那一刻网络怎么样"无关。**
> 这一项藏了很久没被发现，恰恰因为它的失败率是 50%：
> 跑一次看到绿就走的人永远遇不到，跑两次看到一红一绿的人会以为是抖动。
> 只有「连跑 N 次 + 每次抓失败诊断行」才能把二元分叉逼出来。

- 本网络 `raw.githubusercontent.com` **直连 100% 超时**（20s，0 字节，实测 3 次）
- 原逻辑只在「直连**成功**但 >8s」时置 `_RAW_SLOW`——**直连直接超时永远不置位**
- 于是每个文件都白等：直连 20s×2 重试 + 1s sleep + 镜像两次 10s ≈ **61s/文件**

### ③ 新增 `_raw_direct_ok` 的三态纪律
`_RAW_REACH` 存 `probed/ok`，探测一次复用；探测失败（超时）判 `False`，
但**不缓存成"永久不通"的结论性判断**——契约仍是"镜像优先、直连保底"。

## 2026-10-17 v1.6.0 破甲模块接入：吸收外部材料的 10 项解密能力（S148·方案1）

- **缘起**：用户给了 `写源.zip`（4 份材料）。对照现有 9 技能后结论是「生成 py 源码」这一环**完全空白**，

  不引入九秘/八境命名体系（与 M-R 编号冲突）。
- **移植时实测出 6 处真缺陷**（材料自带 self_test 全绿，是**假绿**）：
  1. **PKCS7 不严格**：`aes_cbc_decrypt_and_unpad` 严格去填充失败后，还有个"宽容兜底"——
     末字节落在 1..16 就当长度剥掉。实测 `A*15+\x05` 返回 `b'AAAAAAAAAAA'`，
     **非法填充被当合法数据**。解密失败的正确行为是明确失败，不是猜。
  2. **self_test 假绿**：`except ImportError: pass` + `if encrypted:` + **无条件** print ✅。
     没 pycryptodome 时断言整段跳过却仍报绿。改为 **NIST 向量自证**（不依赖任何第三方库）+
     有库再加测往返 + 无库明确标「往返未覆盖」。
  3. **HTML 误判成 text**：被墙/被 Cloudflare 拦/接口报错全返回 HTML，混进 `text` 与"正常配置"
     长得一模一样——**抓取失败看起来成功了**。新增 `html-page` 单列 + 明确提示。
  4. **Hex 误判成 base64**：十六进制字符集全是 base64 合法字符，原版先走 base64 →
     `89504e47...` 被解成乱码判 `base64-wrapper`。改为 Hex 先判。
  5. **变换链漏识 JS 写法**：原表只有 Python 的 `b64decode`，`atob+JSON.parse` 返回 **[]**——
     明明有 base64+json 两步却报"没有变换"。补 `atob` / `Buffer.from` / `JSON.parse` / `decodeURIComponent`，
     并按**出现顺序**返回（链是有方向的，顺序即信息）。
  6. **XOR 图片靠猜密钥**：原版只试 5 个硬编码 key + `128`，不是那 5 个就永远还原不出，还返回
     `octet-stream/False` 像"没加密"。改为**按图片魔数反推密钥**（`key[i]=data[i]^known[i]` + 周期检测）。

  任何静态规则——只看魔数 → 周期性数据凑出 PNG 头；加 PNG 结构校验 → 又去凑 BMP/WebP。
  **静态规则永远补不完这一课**。最终判据改为**语义**：交给 PIL `verify()` 真解一次，解得开才算图。
  实测 4 正例（PNG/JPEG/GIF 单字节与多字节密钥）逐字节还原，4 反例（随机/文本/零字节/周期串）全部拒绝。

## 2026-10-16 v1.0.5 活跃度趋势外推（S093·roadmap 末项）

**补齐的缺口**：`_activity_verdict` 是**瞬时判定**——只看"此刻"的近30天提交数与
`pushed_at`，回答"现在活跃吗"。但用户真正想早知道的，是"**这条线要废了吗**"——
即**趋势**。一个 `n_commits_30d` 从 30 一路降到 2 的仓库，此刻仍算"活跃"（近30天有提交），
但**三个月后极可能停更**；反过来，提交数持续上升的仓库值得加大依赖。本项补上"看趋势"。

**新增（`probe.py`）**：
- `_forecast_risk(hist, ref_ts, min_pts)`：纯函数。对采样史 `n_commits_30d` 序列做
  **最小二乘线性回归**（抗单点噪声，优于首尾差），斜率 <0 且外推视界内预测值跌破阈值
  →`升高`；斜率 >0 且显著→`增长`；否则`稳定`。视界 `FORECAST_HORIZON_DAYS=60` 天。
- `monitor forecast [--repo] [--json]`：命令封装，逐目标输出风险 + 斜率 + 有效点 + 人话说明。

**三态命门（M-R60，本项最易编造处）**：
1. **`None` 绝不用 0 填充**——某期 `n_commits_30d` 未取到（API 限流等）时，若填 0 参与
   回归，会把"我读不到"当作"该期零提交"，**使斜率虚假变陡 → 谎报"弃更风险升高"**
   （S088 `dirs=[]` 谎报"移除×290" 的同型缺陷）。故 **None 跳过**，有效点 = 非 None 期数。
2. **有效点 < 6 期 → `数据不足`**（明确不预测）——绝不拿 2 期数据外推（那是"编造"非"预测"）。
3. **跨度 < 7 天 → `数据不足`**——分钟级重复采样没有趋势可言（本生态初期正是此情形）。
4. 全 `None` / 空序列 → `数据不足`，**不报任何风险**（假阳性基线）。

**探针**：自检 9 组 → **10 组**，新增第 10 组「活跃度预测」四路断言——真阳性（明显下降
→升高 / 上升→增长）、None 不填充（含空洞序列有效点仍=7 且判升高）、不足不预测
（3 期→数据不足且 risk=None）、假阳性基线（全 None / 空 / 跨度太短→均数据不足）。

**真实数据验证**：用真实采样史（`activity_log.json`，IPTV2 9 期）跑 `monitor forecast`
→ **诚实报「数据不足（有效采样 4 期 < 下限 6 期）」**——因该仓库的采样集中在分钟级窗口，
且多期 API 未取到。**这正是三态的价值**：不硬凑一个"稳定/升高"的结论骗用户。

**探源司 roadmap 至此清零**（原 5 项：多平台 / M18 / harvest 深度抽取 / 活跃度预测 /
迁云端库，全部兑现）。

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| ① | `_load_token` 的 `none`/`fail` 分支**直接 return 而不写缓存** | 状态由 `ok` 变 `none` 后，缓存**滞留旧 token**，`_gh_headers()` 命中脏缓存继续注入已失效凭据 | 新增 `_settle()`——**任何确定结果（含 none/fail）都覆盖缓存**（M-R60⑧ 反例） |

## 2026-10-26 v1.20.8 — packlocal 加 jar 源扫描 + flat 显式化（借鉴用户 pro 包）

**来源**：用户上传 `pro（0930 添加悬浮按钮）.zip` / `PY转换OK专用.zip` 问「有啥借鉴」。
两个包与脚本系同源（本地 py/js/jar 源 → OK影视挂载）。

**实证（demo.json 第 19-25 行）**：jar 本地源也是 `type:3`，但写法不是路径型 api，而是
`api="csp_<名>"` + `"jar":"./jar/xxx.jar"`。FloatSpider 即 `api:"csp_FloatSpider",
jar:"./jar/float-spider.jar"`。这是 drpy jar 源的标准形态（区别于 py/js 的 `./path` 型）。

**改动** `scripts/forge.py`：
1. 收集阶段识别 `.jar`（`_verify_jar`：非空 + 有效 zip，静态级不真跑 Java）；
2. jar site 按 `api="csp_<去后缀名>"` + `"jar":"./<相对路径>"` 生成，与 demo.json 逐字段对齐；
3. 排除 jar 编译产物（`.flock`/`.odex`/`.vdex`/`.class`）；
4. 类型标签改为全称映射（`JS`/`PY`/`JAR`），消除 js/jar 都显 `[J]` 的歧义；
5. `--flat`（默认开）显式化「直接全挂」形态，`_meta.mode=flat`；`--no-flat` 关闭；
6. `_meta` 增 `mode` 键，打印"分发形态"。

**验证**：用 pro 包真实 `Float-Spider.jar` + `人人电影.js` 实测——
`✅ [JAR] Float-Spider.jar — 通过（3/3）` → 生成 site 的 `api/jar/key/name` 与 demo.json 一致；
`⚠️ [JS] 人人电影.js — 无法判定（3/8）` 符合 js 静态口径（默认不收，--keep-unverified 才进）。

**边界声明**：jar 的 `csp_` 标识需在壳子 spider 框架注册才真正可用，本工具只按 demo.json
实证形态生成清单，**不替壳子注册 csp**；jar 能否被 OK影视识别属壳子侧能力，待用户实测确认。

## 2026-10-26 v1.20.7 — packlocal 的 api 默认改相对路径（S205 · 手机实测转圈事故）

**事故**：`脚本系_1026.zip` v2 用 `api="file://storage/emulated/0/脚本系/auto_json.py"`，用户手机
OK影视 5.1.6 点进去**永远转圈、无任何报错**。改 `./auto_json.py`（照用户原工具自带配置
`"api": "./本地PY.JS读取 auto_json.py"`）后一次通过。

**根因**：壳子对 py spider 的 `file://` 绝对路径**静默不执行**——没有日志、没有 toast，
只表现为无限加载。packlocal 原实现（v1.20.6）恰好把 `file://storage/emulated/0/` 写死，
等于把这个坑固化进了工具。

**改动** `scripts/forge.py`：
1. `_cmd_packlocal` 新增 `--file-base`，**默认空 = `./` 相对路径**；
2. `_meta` 增 `api_mode` / `api_prefix` / `说明` 三键，报告每条进清单的源也带 `api`；
3. 控制台打印 api 写法；走 file_base 时打 ⚠ 提示；
4. docstring 与 help 写明事故与判据来源。

**验证**：js 静态路径实测两种模式——默认出 `./demo.js`（api_mode=relative），
显式 `--file-base file://storage/emulated/0/` 出绝对路径（api_mode=file_base）。

**判据（可搬走）**：给壳子分发本地 py/js 源，api 一律 `./` 相对路径；`file://` 绝对路径
在 5.1.6 上对 py spider 静默失败。工具默认值选错 = 每批产物都带同一个缺陷。

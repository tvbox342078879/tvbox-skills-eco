# 网盘分享取料：从一句分享文案到文件清单（S170）

> 外置自 `SKILL.md` §3.14（M-R77⑥ 法③：论证型长节外置）。

## 0. 为什么这一节存在

网盘是**外部分发**渠道。上游作者把整包/源配置传到夸克网盘，跟 GitHub 仓库是**并列的料源**——
很多包只在网盘里发，不在仓库里。用户丢一句「看看里面有啥可借鉴的」，链路就此开始。

但这条链路有一个很强的直觉陷阱：**以为"有链接就能下"**。实测不是。

## 1. 两步走，不要合成一步

```bash
# 第一步：摸清单（只走 API）
tvbox probe harvest pan info --url "<整段分享文案或链接>" [--passcode X] [--json]

# 第二步：取内容（才涉及 CDN）
tvbox probe harvest pan pull --url "<同上>" --outdir ./dl [--match 子串]
```

这两步走的是**两条完全不同的网络路径**，能不能成也完全不同：

| 步骤 | 域名 | 协议族 | IPv4 环境结果 |
|---|---|---|---|
| 摸清单 | `drive-pc.quark.cn` | A 记录正常 | ✅ 200，完整清单 |
| 取内容 | `dl-guest-*.drive.quark.cn` | A + AAAA 都有 | 🚫 412 Precondition Failed |

> ⚠️ **S170 更正**：本节初版写的是「直链域名 IPv6-only、无 A 记录 → 纯 IPv4 出口 412」。
> **那条是错的，已废弃。** 保留这条更正记录，是因为它本身就是一个教训：**归因错了，处置就会把人引到死路。**

## 3. 判据二：412 不是"文件坏了"，但也**不是** IPv6 问题

### 3.1 先看协议族（这条曾经判错）

```python
socket.getaddrinfo('dl-guest-zb-u.drive.quark.cn', 443, socket.AF_INET)
# → 220.181.141.99 / .100 / .101 / .102 / .103 / .104 / .105 / .106   ← 8 个 IPv4
socket.getaddrinfo(..., socket.AF_INET6)
# → 240e:904:800:8100:3::12 / ::13
```

**A 记录和 AAAA 都有。** 逐 IP 用 `--resolve` 直连，`220.181.141.99/.103/.106` **全部 412**。
所以 412 与协议族**完全无关**——换 IPv6 过去还是 412。

### 3.2 对照实验（这才是判据）

| 实验 | 结果 | 排除了什么 |
|---|---|---|
| 裸请求（无任何头） | 412 | — |
| 带 `Referer: https://pan.quark.cn/` | 412 | 防盗链 |
| 带 Chrome UA / 夸克 APP UA | 412 | UA 识别 |
| **故意改坏 token**（`5-a2c384…`→`5-ffffffff…`） | **也是 412，响应体一字不差** | **签名校验** |
| 同一出口访问 `pan.quark.cn` | **200** | 断网 / 全站封禁 |
| 同一出口访问 `image.quark.cn` 图片 | **200** | 出口整体不可用 |
| 同域 API `sharepage/token` | **200** | 域名级封锁 |

**最有力的一条是"改坏 token 也是 412"**：如果拦截发生在签名校验**之后**，
坏 token 应该报 403/401 或不同的业务码；既然两者响应体完全相同，
说明请求在**到达签名校验之前**就被挡掉了。

### 3.3 成因：机房 IP 段被 CDN 边缘节点策略性拒绝

```
HTTP/1.1 412 Precondition Failed
Server: Tengine
Content-Length: 262          ← 固定 262 字节 HTML
Via: ens-cache2.cn8519[,412666]
```

本沙箱出口（`175.24.185.125`，腾讯云上海）属于**数据中心 IP 段**。
网盘 CDN 对云机房 IP 做策略性拒绝，是常见做法（防批量爬取/防盗链）。
`Tengine`（阿里系 nginx 分支）+ `ens-cache`（边缘节点）也印证是**边缘层**拦截。

### 3.4 为什么必须把成因写对

| 成因判断 | 对应的处置 | 后果 |
|---|---|---|
| ~~IPv6 不通~~ | 换 IPv6 机器跑 | **换了过去还是 412**，白折腾 |
| **机房 IP 被拒** | 换家宽/移动网络，或手动下 | 有效 |

判据错了不只是"说法不准"——**它把人指向一个不会成功的动作**。
这和 §3.13 那几条静默缺陷是同一个病根：**归因错位比不报错更毒。**

## 2. 判据一：用户贴的是整段文案，不是干净 URL

真实样本长这样：

```
我用夸克网盘给你分享了「夸克上传文件」，点击链接或复制整段内容，
打开「夸克APP」即可获取。
祄七另枫诶并闭页冉为喔汢 /~d9803bYsb2~/   ← 这是「口令」
链接：https://pan.quark.cn/s/9d5b78140523  ← 真正的 pwd_id 在这里
```

口令 `/~d9803bYsb2~/` 长得**极像**一个 id。拿它去查分享会返回「分享不存在」，
而真正的原因是**解析错了**——这是典型的"报错指向错误的位置"。

`pan_parse_share()` 只认 `/s/<id>`：

```python
m = re.search(r'pan\.quark\.cn/s/([0-9a-zA-Z]+)', text)
```

反例必须也成立：`/~d9803bYsb2~/` 单独输入应返回空串，不许误认。

## 3. 判据二：412 不是"文件坏了"

> 见上一节（§2.2–3.4 的对照实验）。一句话：**正确 token 与坏 token 同样 412、
> 同出口其他站点 200 → 边缘节点按来源网络段拒绝，与协议族/签名/UA 均无关。**

把它并进「下载失败」，就等于把「我这边到不了」说成「你的文件有问题」——
M-R113 的**监测面缺口伪装成健康度**，这次伪装成了"文件失效"。

代码里 412 单独计数、单独文案、单独处置建议：

```python
except urllib.error.HTTPError as e:
    if e.code == 412:
        cdn_reject += 1
        print(f'  🚫 {f["name"]}：412 —— **CDN 拒绝本出口，非文件问题**')
```

## 4. 判据三：`format_type` 是"改名包"的铁证

夸克 API 的 `format_type` 报的是**文件真实容器格式**，不是后缀。实测这一份分享：

| 文件 | 大小 | `format_type` | 判断 |
|---|---|---|---|
| `base(2).apk` | 25.8MB | `application/vnd.android.package-archive` | 真 APK |
| `base(1).apk` | 7.1MB | `application/vnd.android.package-archive` | 真 APK |
| `base.apk` | 2.7MB | **`application/zip`** | 容器是 zip，后缀是 apk |
| `base(3).apk` | **37.3KB** | **`application/zip`** | 改名的 zip/文本 |

两条交叉判据：

- **`format_type` 含 `zip` 但后缀是 `.apk`** → 容器不是 APK，是被改了名的包；
- **`.apk` 小于 100KB** → 正常 APK 不可能这么小（最小空壳也有几 MB）。

`info` 会把这两条都拎出来单独预警，因为它们决定了"取回来该当安装包用、还是当配置包拆"。

## 5. 处置阶梯（按代价从低到高）

遇到 412 时，**不要重试**（出口不可达，重试一百次还是 412）：

1. 在有 IPv6 的机器上跑同一条命令；
2. 用夸克 App / 网页版手动下载，放进指定目录；
3. 让分享者换一个直链可公网访问的网盘。

> **清单已拿到就等于"知道里面有什么"。** 别把"取不到"当成"里面没东西"——
> 前者是能力边界，后者是错误结论。

## 6. 接口路径备忘（哪些还活着）

| 接口 | 状态 |
|---|---|
| `POST /1/clouddrive/share/sharepage/token` | ✅ 换 `stoken`（`pwd_id` + `passcode`） |
| `GET /1/clouddrive/share/sharepage/detail` | ✅ 列目录（需 `pwd_id`/`stoken`/`pdir_fid`） |
| `POST /1/clouddrive/file/download` | ✅ 换直链（需 `fids` + `fids_token` + `pdir_fid`） |
| `POST /1/clouddrive/share/sharepage/download` | ❌ **已废弃，404** |
| `POST /1/clouddrive/share/sharepage/save` | ✅ **已打通（S217+S218·2026-10-24 夸克+UC 双平台端到端实测）**，要求登录 |

`share_fid_token` 要从 `detail` 的每个文件对象里取，**不是** `stoken`。
漏了它 `file/download` 会返回空 `download_url`。

## 6b. 转存（save）实测要点（S217）

- **登录态**：cookie 含 `__pus`/`__puus`/`__kps`/`__ktd`/`__uid` 组即有效，**不需要 `ck` 字段**
  （手机浏览器 Cookie 面板看不到 `ck` 属正常——它是 httpOnly；整串复制请求头 Cookie 即可）。
  快速验证法：拿 cookie 调 `GET /1/clouddrive/member?pr=ucpro&fr=pc`，HTTP 200 且业务码 200 即有效。
- **参数铁律**：`save` 的 `fid_list` / `fid_token_list` 必须是 **JSON 数组**
  （`["fid1","fid2"]`）——**逗号分隔字符串会 500 `code=15000 inner error`**（实测两个分享一致复现）。
- **异步任务**：save 返回 `task_id`，须轮询 `GET /1/clouddrive/task?task_id=..&retry_index=N`
  至 `status=2`（完成）；`status=3` 为失败。
- **边界**：`is_owner=1`（自己的分享）不能转存回自己网盘；转存全程走 API 域，不碰 CDN 412。
- **排障改进**：`_pan_req` 的 HTTPError 已改为读出服务端响应体（旧版只报 `HTTP 500`，丢诊断信息）。
- **双平台（S218）**：`PAN_PLATFORMS` 已支持 `quark`（`drive-pc.quark.cn` / `pr=ucpro`）与
  `uc`（`pc-api.uc.cn` / `pr=UCBrowser`），接口路径同构、`_pan_req` 按 `platform` 切域名与 `pr`。
  登录态加载经本轮回补泛化为 `_load_pan_cookie(plat)`：夸克读 `.quark_cookie`、UC 读 `.uc_cookie`，
  不再硬编码夸克。UC 分享实测 `drive.uc.cn/s/2efbbbb79b594` 成功转存 3 文件；
  UC 登录页 `https://drive.uc.cn/`，分享格式 `https://drive.uc.cn/s/<id>`。

# 附：单文件资源容器 MSITEPK2（S171）

> 来源：用户上传的三个 zip 之一 `base.apk`，其 `assets/site.pak` 就是一个 MSITEPK2 容器。
> **上一轮我判它「数据区加密，放弃硬解」，那是错的**——密钥就躺在同一个 apk 的 `classes.dex` 里。
> 记这条不是为了那个包，是为了这个判断错误本身：**"放弃"之前先问一句，解密逻辑在哪一层。**

## 1. 三类分发形态（这轮看全了）

| 形态 | 代表 | 特征 | 打开难度 |
|---|---|---|---|
| **明文目录树** | `base(1).apk` 的 `assets/`（未加密时） | 一文件一资源，index 靠文件名 | 零 |
| **加密单文件容器** | `base.apk` 的 `site.pak` | 一个 2MB 文件装 78 个资源 | 需 key（**key 在 apk 内**） |
| **逐文件加密的目录树** | `base(1).apk` 的 `assets/`（实际状态） | 每个 html/js 都单独加密，**共同前缀仅 15~36B** | 等于随机 IV，逐文件 Key 不明 |

第三类的判据值得记住：**两个文件头部相同的字节数只有十几到几十个，说明 IV 随机、块间链式**——
这种结构下"找规律"是徒劳的，只能找 key。这也是我最后没有硬解 `base(1).apk` 的原因，**不是懒，是路径明确而成本高**。

## 2. MSITEPK2 格式（反编译得到，非猜测）

```
magic(8)   = "MSITEPK2"
count(4BE) = 条目数
每条 24B 起：
  name_len(2BE) + name(UTF-8) + off(4BE, 相对 payloadStart) + len(4BE) + iv(16B)
头部读完位置 = payloadStart
数据区每条：AES-256-CBC(PKCS5) 解密 → zlib 解压（标准头 78 da，**不是 raw deflate**）
```

来源类 `com.moliys.tvbox.SitePak`：

| 成员 | 作用 |
|---|---|
| `MAGIC` / `readShort` / `readInt` | 头部解析（大端） |
| `create([B pak, [B key)` | **断言 `key.length == 32`** → AES-256 |
| `inflate([B)` | `InflaterInputStream` → **标准 zlib 头** |
| `read(String)` | 按 index 取 `off/len/iv` → Cipher 解密 → inflate |

密钥来自另一个类 `com.moliys.tvbox.SiteKeys` 的静态常量 `SITE_KEY_HEX`（64 hex = 32 字节）。
**它是手写 Java 类，只有 `<init>` 没有 `<clinit>`** → 说明是编译期常量内联，hex 串以普通字符串常量
躺在 dex 字符串池里。`probe pak` 就按「dex 里唯一的 64 hex 串」去找，比 grep `key` 稳得多
（dex 里 `key` 出现上千次）。

## 3. 这层加密的实际意义：**防扒 ≠ 加密**

key 在 apk 里，装了应用的人都能取。所以它挡的是"随手 curl 一下"，不是"有心人"。
**做分发时别指望这层能护住数据**，它的价值在别处——见下条。

## 4. 真正值得借鉴的设计（不是格式，是思路）

这个包把 78 个资源（源清单 `api/*.json`、m3u 列表、70+ 站点图标、健康数据 `health.json`、
整个前端 `index.html` 133KB）压进**一个 2MB 文件**：

- **一次请求拿全站**，不做逐文件往返；
- **不被按文件粒度的 CDN 缓存策略穿透**（对国内这些时常抽风的 raw 域名很实际）；
- **资源清单内嵌**，不依赖目录索引服务（jsDelivr/GitHub API 挂了也不影响）；
- **整体签名/整体替换**，版本升级就是换一个文件。

对应到探源司的诉求：`lightjson` / `repack` / `prune` 都在**操作目录树里的多个文件**，
而"整包外发"这件事，**单文件容器天然更抗干扰**。`probe pak` 就是为此留的解包口。

## 5. `health.json` 的设计（顺带记，可借鉴）

92 个接口，每条同时记录**主址 + 4~5 个镜像各自的结果**：

```json
{"ok":false,"code":0,"ms":0,"err":"DNS","doh":true,
 "urls":{"https://tvbox.moliys.icu/...":{"ok":true,"code":200,"ms":18,"size":10338},
         "https://0.cdz.qzz.io/...":{"ok":true,"code":200,"ms":702,"size":5344}}}
```

两个点值得抄：

1. **`ok:false` 但 `urls` 里全 200** —— 主址失败、镜像可用。这不是矛盾，是**如实记录"哪条路通"**。
   我们 `heal` 只看一个 URL 就判死活，就是这个包在避免的坑。
2. **`doh:true` 把"DNS 失败但用 DoH 能解"单列成黄**（`st-warn`），不是红。
   这正好对上本技能 ③ 号缺陷（412 并进失败、证书过期判死）：**失败要分因，别折叠**。

另注：这个包自身的站内 URL 已大面积 404，但 `health.json` 仍写着 `ok:true size=17935`——
**健康数据本身也会过期**，别把它的结论当现状，要自己再测一遍。

# S199 · 发布源直连包 + 生命周期声明（两类新型监测目标）

> 由来：小虎斑系 TVBox 壳的配置文件是「对象存储直连包」，无 git 历史、无 commit——
> 传统 monitor 只认 GitHub 仓库，对它**是监测黑洞**。小虎斑又在 mark.json 自报
> `version=26.10.18-仅供测试`，作者自报态与实测活跃度是两个正交维度。
> 本文件落地两类升级（代码见 `scripts/probe.py`）。

## 一、发布源直连包（pub-package 型）

### 1.1 登记（结构字段本地真源）
编辑 `scripts/monitor_pubsources.json`。**双锚点**实测示例（2026-10-23 核入）：

```json
{
  "pubs": {
    "pub-xiaohuban": {
      "kind": "pub-package",
      "名称": "小虎斑·发布信号锚点（mark.json）",
      "发布源URL": "https://xiaohuban.cn-nb1.rains3.com/mark.json",
      "包类型": "json(含 version 自报)",
      "关联底包": "底包·小虎斑系",
      "监测周期": "每周"
    },
    "pub-xiaohuban-zip": {
      "kind": "pub-package",
      "名称": "小虎斑·更新包直连（zip 实体）",
      "发布源URL": "http://38.76.197.172:25252/...编码后的中文路径.../小虎斑.zip",
      "包类型": "zip(301 重定向→38.76.197.42)",
      "监测周期": "每周"
    }
  }
}
```

> **为什么双锚点**：mark.json 是「作者说发了新版没」的信号源（小、含 version 自报，
> 也供生命周期声明维度）；zip 是「包实体变没变」的实体锚点（4.56MB，取前 64KB 指纹）。
> 两者互补——信号源换了但包没动，或包被替换但 version 没改，都能交叉看出来。
>
> 结构字段只存 companion，每次 `load_targets` 按 id 注入 `kind`，绕开云端非标列丢失。

### 1.2 探针
`scan_pub_source(url)`：HTTP `HEAD` + `Range:0-65535` 取前 64KB 算 sha12，三态——
- **取到**（200/206，有元信息）：返回 `bytesize / sha12 / last_modified / etag`
- **取不到**（404/410 / 域名挂）：`alive='已失效'`
- **无法判定**（超时 / 412 / 5xx / 编码异常）：`alive='无法判定'`

不整包下载，大包也快；与快照比对即知「包在不在 / 变没变」。

### 1.3 调度与展示
`monitor check` 按 `kind` 分流（`_probe_target`）：pub-package → `_probe_pub_source`。
打印单列「📦 发布源型目标」，显示**包大小 / 更新时间**而非"文件数 / 提交数"（后者对该型不适用）。

## 二、生命周期声明维度

### 2.1 与实测活跃度的正交关系

| 维度 | 来源 | 含义 |
|---|---|---|
| 实测活跃度 | 近30天提交 / 推送时间 / 包更新时间 | "它现在动不动" |
| 生命周期声明 | 作者自报（mark.json 的 version / 正式·测试·弃更·停止） | "作者说它是什么状态" |

两者独立；只有交叉才有意义（自报"测试" ≠ 实测"活跃"）。

### 2.2 探针与交叉
- `scan_lifecycle_decl(t)`：对 pub-package 抓 `{base}/mark.json`；对 repo 型抓 `raw/main|master` 的 `mark.json / version`。**递归解析**（mark.json 真实结构是数组 + 嵌套 list，version 在 `list[0].version`，顶层 `.get` 直接失效）——见 §三 已知坑。三态：取到 / 无自报 / 无法判定。
- `cross_lifecycle(decl, activity)` 四象限：
  - 声明`弃更/停止` ∩ 实测`活跃/停滞` → **⚠️冲突**（声明可能过期或非同一分支）
  - 声明`正式` ∩ 实测`停滞/归档` → **⚠️风险**（长期不动，疑似隐性停更）
  - 声明`测试` ∩ 任意实测 → **ℹ️提示**（仅供测试源，稳定性低）
  - 其余 → 一致

### 2.3 调度
`monitor check` 对 pub-package 型**自动**跑交叉；repo 型仅在 `--repo <单目标>` 指定时跑（避免常规全量巡检拖慢）。

## 三、实测记录与已知坑（2026-10-23 核入）

### 3.1 实测数据

| 锚点 | 结果 | 关键值 |
|---|---|---|
| mark.json | 存活 | 1151B / sha12=`6b3f31613795`（三次连探一致）/ ETag=`a6bcd247…` / 更新 `2026-10-18 07:21:13` |
| 更新包 zip | 存活 | 4,563,571B / sha12=`f56ce351541a` / ETag=`6ad4731a-45a273` / 更新 `2026-10-18 07:19:54` |

### 3.2 坑一：mark.json 是数组 + 嵌套 list（已修复）
真实结构为
`[{ "name":..., "list":[{ "name":"小虎斑本地更新", "version":"26.10.18-仅供测试" }, ...] }]`
—— 是**数组且 version 嵌套在 `list[0].version`**。原 `scan_lifecycle_decl` 假设顶层对象直接 `.get('version')`，对数组抛异常走兜底 → 自报态误判为"正式"、自报版本空。已新增 `_extract_decl()` 递归遍历所有层级修复。

### 3.3 坑二：301 跨 IP 重定向（探针已带 -L，登记需用原地址）
`38.76.197.172:25252` 返回 **301 → `38.76.197.42:25252`**（同 C 段换 IP）。不跟重定向只拿到 162B 跳转页、正文非 zip。探针 `curl` 已带 `-L` 自动跟随，故 companion 登记**作者原发布地址**即可（IP 变更由 301 兜住）。

### 3.4 坑三：二进制正文被文本解码炸（已修复）
`_sh()` 用 `subprocess.run(text=True)` 按 UTF-8 解码 stdout；zip 前 64KB 含非法字节 → `UnicodeDecodeError` 被 `except` 吞成 `rc=-1` → 正文指纹恒空、误报"正文取不到"。已新增 `_sh_bytes()` 取原始 `bytes` 交 `_content_sha`，zip 指纹正常。

> 另一层隐性危害：**文本锚点经 text 往返也会产生伪指纹**。mark.json 旧路径得 `ea1f25a99ece`（解码再编码失真），改 `_sh_bytes` 后原始 bytes 得 `6b3f31613795`，连探三次一致。若沿用伪指纹，"内容变更检测"会天天误报。
> 通用教训：**凡是抓二进制（zip/jar/so）一律走 `_sh_bytes`；凡是要做指纹比对的正文，也一律取原始 bytes**，不要用文本版 `_sh`。

### 3.5 坑四：HTTP 日期解析缺失 → 活跃度恒"无法判定"（已修复）
发布源型的"更新频率活跃度"依赖 `Last-Modified` 头，而该头是 RFC 1123 格式（`Sun, 18 Oct 2026 07:21:13 GMT`）。`_parse_ts` 原只认 ISO8601 / `YYYY-MM-DD`，对 HTTP-date 返回 None → 活跃度恒"无法判定"，该维度形同虚设。已加 `email.utils.parsedate_to_datetime` 回退（置于既有回退之后，不影响 GitHub/GitLab/Gitee 时间解析）。

### 3.6 验证
自测脚本三态 / 四象限全绿；真实双锚点闭环：mark.json 存活（活跃度=活跃）+ 生命周期声明=测试 + 交叉=提示；zip 存活（活跃度=活跃）且指纹 `f56ce351541a` 取到。

### 3.7 坑五：发布源型活跃度口径缺失（整合验证发现，已修复）
`monitor check` 主流程第 2331 行 `act = _activity_verdict(rec.get('n_commits_30d'), rec.get('pushed_at'))`。
发布源型无 commit 维度（`n_commits_30d=None`），原 `_probe_pub_source` 虽算出
`_lm_ts`（更新时间时间戳）却**没赋给 `rec['pushed_at']`**，于是 `pushed_at=None`
→ `act` 恒为"无法判定"——即便 `rec['activity']`（基于更新时间）明明是"活跃"。
连锁后果：① 展示段（2428 行）印"活跃度=无法判定"；② 生命周期交叉（2442 行）
基于账面活跃度"待查"而非真实"活跃"，交叉结论失真。
**修复**（probe.py:2094）：`_probe_pub_source` 末尾加 `rec['pushed_at'] = _lm_ts`，
让主流程 `_activity_verdict(None, _lm_ts)` 走"按推送时间判定"口径，与仓库型统一。
修复后：`act=活跃`、展示=活跃、mark.json 交叉=提示（自报测试∩活跃）。

### 3.10 坑六：发布源型被误报"部分字段未取到"（已修复）
S190「未取到必须自带原因」逻辑（第 2457–2464 行）假设所有目标都有 `n_files/n_commits_30d`，对取不到者追加 `⚠️ 部分字段未取到`。但发布源型本就只有"包大小/更新时间"维度、不产生文件数/提交数——对它报"未取到"是把"不适用"说成"没取到"（同 S204 对 `domain-set` 的定位）。原代码第 2459 行只排除 `domain-set`，**漏了 `pub-package`**。
**修复**（probe.py:2459）：排除条件由 `t.get('kind') != 'domain-set'` 改为 `t.get('kind') not in ('domain-set', 'pub-package')`。zip 真实命令复验：note 仅 `发布源直连包可达`，不再出现误报。

### 3.11 用法澄清：`--repo` 是精确匹配，非子串
`monitor check --repo <值>` 的筛选（第 2282 行 `a.repo in (仓库URL, id)`）对**元组**的 `in` 是**成员精确相等**，不是子串。故 `--repo pub-xiaohuban` 只精确命中 `id=pub-xiaohuban`，**不会**子串命中 `pub-xiaohuban-zip`。双锚点需分别 `--repo pub-xiaohuban` / `--repo pub-xiaohuban-zip` 跑，或 `monitor check` 全量（含全部 124 目标）。这是 `monitor check --repo` 的全生态一致语义（2626/2675 行同款），非缺陷——不要为"一次跑双锚点"擅自改成子串匹配。

### 3.12 坑七：发布源健康字段云端持久化缺口（已修复）
`cmd_monitor_check` 在 2342–2368 行把发布源探测结果写回 target 的 **18 列顶层键**
（`存活状态`/`内容指纹`/`活跃度`/`上次检查`/`变更摘要`/`下次到期`）——这些本就是云端
`_cloud_row_to_target` 的 18 固定列，**理论上能 round-trip**。但 `_cloud_save_targets`
（904 行）对 `domain-set` 型显式过滤只留 18 列（避开整条拒收），对 `pub-package` 却走
`else` 分支 `rows.append(t)` 原样全量上传。发布源型 target 含 `kind`/`发布源URL`/`包类型`
（非标列）+ `平台='发布源'`（来自 `_inject_pub_sources` 兜底分支 466 行，非合法 select 值），
**非标列触发云端整条拒收 → 连 18 列健康字段也上不去云**，监测结论无法持久化。
**修复**（probe.py:917）：`if t.get('kind') in ('domain-set', 'pub-package')` 纳入同一过滤
分支；平台兜底由 `=='域名型'` 泛化为 `not in ('GitHub','Gitee','GitLab','其他')`，
自动把 `发布源`/空/其他非标值兜底成 `'其他'`。
**验证**（沙箱云端不可达，mock `_cloud_upsert` + 真实函数，M-R135）：构造 check 后发布源型
target → `_cloud_save_targets` → 上传 row 仅含 18 列、平台='其他'、健康字段（存活/活跃/
指纹/上次检查）保留；`_cloud_row_to_target(row)` 读回无损；domain-set 分支回归不受影响。
**好处**：发布源型监测结论（存活/活跃/指纹/上次检查）现可随 `monitor check` 双写云端，
跨会话不再只依赖本地 `monitor_targets.json` 兜底。结构字段（kind/发布源URL/包类型）仍留
本地 companion（与 domain-set 同口径）；`名称` 非云端列、随过滤剥离，发布源型在云端以
`id` 识别（与 domain-set 一致，非缺陷）。

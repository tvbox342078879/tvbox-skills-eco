# S169·监测台两处静默缺陷的正本

> 外置自 `SKILL.md` §3.13（M-R77⑥ 法③）。本文件是**正本**，SKILL.md 只留索引与判据表。
> 涉及代码：`scripts/probe.py` 的 `_cloud_upsert` / `_cloud_save_targets` / `_probe_repo` / `cmd_monitor_check`。

## 一、这两条的共同形态：不报错

`monitor check` 曾有两种"看不出坏"的坏法，症状都不是报错，而是**结果一直不变**：

| # | 现象 | 用户能看到 | 真实情况 |
|---|---|---|---|
| ① | `上次检查` 永远「—」、`monitor due` 永远"全部到期" | 每轮巡检都重跑全量 | 时间列**根本没写进云端** |
| ② | 4/6 仓库「存活=无法判定」，但同一次的文件数/提交数都有值 | 看着像"网络抽风" | 存活判据只看主页，不看已经拿到的 API 数据 |

两条都属 `M-R113`（监测面缺口伪装成健康度）：「无法判定」比「死」温和，
而且它**每轮都会重复出现**——重复久了就变成背景噪音，没人再追。

## 二、缺陷 ①：date 列被当成 text 写，平台静默丢列

### 症状

巡检跑完，本地备份 `monitor_targets.json` 里明明有
`"上次检查": "2026-10-19T06:10:17Z"`，云端回读却是空串。

### 定位过程

1. 先确认不是本地问题：`save_targets` 双写，本地成功。
2. 再确认不是写入被拒：单条更新回执 `{"results":[{"index":0,"id":"juwGKJdQrIh1yjbGTvGqO9","success":true}]}`。
3. 换值格式逐个试，全部 `success: true`、全部回读空——**回执不可信**。
4. 同批写一个普通文本列做对照：`变更摘要` 落了、`上次检查` 没落 → **是列本身的问题**。
5. 读库结构 `get_database_schema.py`：

   ```
   {"id": "E4vHJyF0", "name": "上次检查", "type": "date"}
   {"id": "HDdPgRev", "name": "下次到期", "type": "date"}
   {"id": "S2ap4dPb", "name": "变更摘要", "type": "text"}
   ```

6. 按 `date` 类型写 `{'date': '2026-10-19T06:10:17Z'}` → 立刻回读可见。

### 载荷对照（均为实测）

| 写法 | 回执 | 回读 |
|---|---|---|
| `{'text': '2026-10-19T06:10:17Z'}` | `success: true` | **空** |
| 纯字符串 `'2026-10-19T06:10:17Z'` | `{"error": "records[0].properties 校验后为空，无有效字段"}` | 空 |
| `{'number': 1792390076}` | `success: true` | **空** |
| `{'date': 1792390076000}` | `{"error":"批量更新记录请求失败: code=11607; msg=json: cannot unmarshal number…"}` | 空 |
| `{'date': '2026-10-19T06:10:17Z'}` | `success: true` | `2026-10-19T06:10:17Z` ✅ |

**关键**：除正确的 `{'date': ISO串}` 外，其余写法**要么报错、要么假成功**。
而假成功那几种（text / number）给的是和正常写入**一模一样**的回执。

### 修法

`_cloud_upsert` 加 `date_cols` 参数，走独立分支：

```python
elif k in dat:
    props[k] = {'date': str(v)}        # S169：date 列不是 text
```

`_cloud_save_targets` 传入 `date_cols=('上次检查', '下次到期')`。

### 怎么保证不再复发

`self-check` 新增命门探针 `上云date列不被当text写丢`，三件套：

- **捕获**：不传 `date_cols` 或传错，`上次检查` 被包成 `{'text':...}` → 判否；
- **假阳性基线**：同批的 `变更摘要` 必须仍是 `{'text':...}`、`存活状态` 必须仍是 `{'select':...}`
  ——防止"为了修 date 把 text 也改成 date"这种反向错；
- **清理后清零**：不传 `date_cols` 时退回 `text`，证明起作用的是参数而不是硬编码。

探针用内存桩替换 `_cloud_id_map` / `api`，只截获即将发出的 `properties`，**不打网络、不写库**。

实测双向：注入 `{'text'}` → `❌ 捕获=否`、`28/29`、rc=1；还原 → `29/29`、rc=0。

## 三、缺陷 ②：存活只看仓库主页

### 症状

同一轮巡检里：

```
⚠️ TVBox_live   存活=无法判定  活跃度=活跃  文件数=29    近30天提交=100
⚠️ tvbox        存活=无法判定  活跃度=活跃  文件数=778   近30天提交=100
```

**活跃度、文件数、提交数全取到了，存活却说无法判定**——自相矛盾。

### 实测数据

| 目标 | `github.com/{o}/{r}` | `api.github.com/repos/{o}/{r}` |
|---|---|---|
| lxcjy/IPTV2 | 000（25s 超时） | 200 |
| songlees355-wq/okay | 000（25s 超时） | 200 |
| Supprise0901/TVBox_live | 000（25s 超时） | 200 |
| cluntop/tvbox | 200（5.9s） | 200 |

`github.com` 本网络**时通时断**；`api.github.com` 稳定 200。
是否判成"无法判定"，只取决于跑的那几秒主页通不通——**结论随网络抖动而变**。

### 修法：判据分层

| API 状态 | 存活结论 | 依据 |
|---|---|---|
| `ok` | 存活 | API 能返回 repos 元信息，仓库必然存在 |
| `notfound` | 已封禁/删除 | API 404 比主页 404 权威 |
| `ratelimit` / `fail` | 退回主页探测结论 | 此时主页是唯一证据源 |

主页探测结果**不丢**，记进 `rec['alive_by']`；非主页判定的会在 `note` 追加
「存活依据=API元信息（仓库主页不可达）」，并且 `monitor status` 会在该行下缩进显示。

### 为什么要在 status 里显形

「存活」是结论，不是证据。如果只在 `check` 的输出里说一次，下次看 `status` 就只剩一个"存活"，
用户无法区分"主页通"和"主页挂但 API 说活着"。实测现状：

```
  IPTV2              GitHub  存活         停滞     2026-10-19T06:19:32
                     └─ GitHub API 正常；存活依据=API元信息（仓库主页不可达）
```

## 四、顺手修的一处误导文案

`monitor check` 的配额预检原文一律「或等配额重置后重试」。
但 `reset` 时刻已过（`stale`）时，等待时间是 0 分钟，那句话会把人往"再等等"上带——
实测 14:01 显示「重置 4 分钟后」，到点再查仍是 0。

现在按 `stale` 分岔：

- 未过期 → 「或约 N 分钟后重试（reset HH:MM）」；
- 已过期/陈旧 → 「⚠️ reset 时刻已过/数据陈旧——**等不会变好**，唯一确定解法是配 token」。

`probe token` 的匿名额度提示同样加了这层分岔。

> 附一条实测备忘：匿名 60/h 配额下，两次连续查询 `rate_limit` 得到的 `reset`
> 可能相差 2 分钟（实测 14:06:00 与 14:07:56）——那是**同 IP 不同配额桶**的抖动，
> 不是同一窗口的重置承诺。所以「到点就恢复」不成立，只有「确实回读到 remaining 回升」才算恢复。

## 五、教训（写进判据，不只写在这里）

1. **「回执成功」和「值真的进去了」是两件事。**
   S143 定过这条，但只覆盖"整批被拒"；单列静默丢弃照样 `success: true`。
   凡写入，验收标准只能是**回读**。
2. **凡判定，验收标准只能是"说清凭什么"。**
   存活=API 还是主页、文件数=本期取的还是上期留的，都要能追。
3. **结论随网络抖动而变 = 判据选错了证据源。**
   选证据源要选"稳定且权威"的那个（API），而不是"看起来最直观"的那个（主页）。

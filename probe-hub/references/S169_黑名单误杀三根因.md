# S169·黑名单误杀的三处根因（正本）

> 涉及代码：`scripts/probe.py` 的 `judge_level` / `source_fp` / `cmd_bl_mark` / `cmd_bl_audit` / `_alive_line`，
> `scripts/livecheck.py` 的 `_curl` / `_err_kind` / `check_auto_ignore_cert`。
> 外置于 `SKILL.md` §3.5.1 判据 ⑥⑦。

## 〇、这轮是怎么发现的

用户指令「推不动的放进历史遗留，按你说的推进」，我选了不依赖 GitHub API 的 `blacklist` 模块。
没按"有多少条"汇报，而是**抽 L1 实测**——172 条里先抽 17 条证书类的，就捞出 5 条误杀。

> 如果只统计"L1 有 172 条、L2 有 51 条"，这些误杀一条都发现不了。

---

## 一、根因①：`judge_level` 只看失败次数，不看**为什么**失败

### 原实现

```python
if fails >= L1_MIN_FAILS and gap >= L1_MIN_GAP_DAYS:
    return 'L1精确黑', ...
```

只问「失败几次、隔了几天」。于是：

| 失败原因 | 失败 2 次 + 间隔 3 天 | 判得对吗 |
|---|---|---|
| DNS 无 A 记录（域名真没了） | L1 确认死 | ✅ 对 |
| 站点返 404 | L1 确认死 | ✅ 对 |
| **证书过期** | L1 确认死 | ❌ **错——续期即活** |
| 测活超时（我方网络） | L1 确认死 | ❌ 错——我这边到不了 ≠ 它死了 |

### 实测误杀

| 源 | 被判 | 跳过证书校验后的真实情况 |
|---|---|---|
| `ryzy.tv/api.php/provide/vod/from/rym3u8/` | L1 确认死 | ✅ 通过：8.7 万条，播放地址真拉得动（130KB） |
| `lz.118318.xyz/api.php/provide/vod/at/xml` | L1 确认死 | ✅ 通过：30 万条，307 条播放地址，分片拉到 **92KB** |
| `taopianapi.com/cjapi/sda/vod/json` | L1 确认死 | ✅ 通过：有真实播放地址 |
| `taopianapi.com/cjapi/mc/vod/json.html` | L1 确认死 | ✅ 通过：有真实播放地址 |

`ryzy.tv` 证书 `notAfter=Sep 17 23:59:59 2026 GMT`，已过期 32 天，但接口数据**今天仍在实时更新**
（`vod_time=2026-10-19 14:28:52`）——服务活着，只是运维忘了续证书。

### 修法

`judge_level` 增加 `reason` / `detail` 入参，证书类关键词命中即**封顶 L2**：

```python
_txt = f'{reason or ""} {detail or ""}'
_cert = any(k in _txt for k in ('cert_expired', 'cert_invalid', '证书'))
if _cert:
    return 'L2观察', f'证书类失败（{fails}次）·续期可恢复，封顶 L2 不判死—原始原因：{_txt[:60]}'
```

**为什么不直接判活**：证书过期意味着任何正常客户端（TVBox 也是）都会握手失败。
判「通过」会让它进成品库然后转圈。**封顶 L2** 是准确的位置——拦下强制测活，但不判死。

## 二、根因②：`_curl` 把失败原因塌成 000

`livecheck._curl` 任何失败都返回 `code=0`，上层只知道"不可达"，无从分辨：

- DNS 没有 A 记录 → 域名真没了
- 连接超时 → 我方网络到不了
- 证书过期 → 内容可能好好的

于是 `pardon`（平反）永远过不了"实测通过"这一关——**误杀无法自愈**。
这正是那 4 条一直躺在 L1 里的原因。

### 修法

`_curl` 解析 stderr 关键词 → `_last_err_kind`：

```python
def _classify_err(err):
    if 'certificate' in err and 'expired' in err: return 'cert_expired'
    if 'certificate' in err: return 'cert_invalid'
    if 'could not resolve' in err ...: return 'dns'
    if 'refused' in err: return 'refused'
    if 'timed out' in err ...: return 'timeout'
    ...
CERT_KINDS = ('cert_expired', 'cert_invalid', 'tls')
```

`check_vod` 在"全部不可达"分支把类别带进证据串：

- 证书类 → `【证书类】证书已过期（续期即恢复，非站点失效；建议跳过校验复验内容）`
- DNS → `DNS 无 A 记录（域名真没了）`
- 超时 → `连接超时（可能在墙/在挂，不一定是死）`

### 复验通道（边界写死在实现里）

`check_auto_ignore_cert()` **只用于证书类失败的复验**：

- 只在 `_last_err_kind in CERT_KINDS` 时被 `_alive_line` 调用；
- 结论强制带 `【跳过证书校验】` 前缀——看的人一眼知道这份证据的分量；
- 它**不会**让源直接进正常库，只服务于 `pardon` 这类复验动作。

实测：`okjx.cc`（证书错误）跳校验后仍是 HTML 拦截页 → 拒绝平反；
`taopianapi.com/home/cjapi/vod/` 跳校验后 404 → 拒绝平反。
**判据没被放宽，只是把"看不到内容"和"内容坏了"分开了。**

## 三、根因③：黑名单只进不出，没有体检

`mark` 要 `--yes` 手动写，自动链路没有；平反要人先起疑。**误杀只能靠偶然发现。**

### 新增 `blacklist audit`

```bash
tvbox probe blacklist audit --sample 24          # 预演
tvbox probe blacklist audit --sample 24 --yes    # 复验通过的自动平反（默认每轮最多 1 条）
```

设计要点：

| 项 | 做法 | 为什么 |
|---|---|---|
| 抽样 | **确定性等距**（按指纹排序后等距取） | 随机抽样两次跑出不同结果，无法判断"误杀变多了"还是"抽到的不同" |
| 判据 | 直接复用 `_alive_line` | 与 `pardon` 同一把尺子（M-R38 单一事实源） |
| 分类 | DNS 无记录 → **确认死**；超时/证书 → 无法判定 | 按证据强度分，不按"消息里有没有'不可达'"分 |
| 平反 | 默认每轮最多 1 条 | 防止一次体检把大批条目冲动平反 |

### 三态分类的坑（已修）

初版把「DNS 无 A 记录」算进了"无法判定"，首跑结果 7 死 / 17 无法判定。
实测 46 条 DNS 失败的域名，用公共 DNS（alidns）复核**全部无 A 记录**——域名真没了，属确认死。
修正后同一批抽样：12 死 / 12 无法判定。

> 教训：分类不能按"消息字面"分，要按"证据有多强"分。

## 四、附带修掉的脏数据

### 症状

失信库有一条 `https://https://raw.githubusercontent.com/YanG-1989/m3u/main/Gather.m3u`（协议头重复）。
归一化后得到 `https/raw.githubusercontent.com/…`——**host 位置混进了协议名**。

### 为什么原逻辑没拦住

`source_fp` 的剥代理分支要求 `m.start() > 0`；而这条 URL 的第二个 `://` 正好在位置 0
（`https://` 之后紧跟 `https://`），不触发 → 直接落到常规归一化 → 产出无效指纹。

后果：这条指纹永远匹配不到真实 api（真实 api 归一成 `raw.githubusercontent.com/…`），
白占一个 L1 名额，复验时永远"不可达"、被算作正常。

### 修法

```python
if re.match(r'^https?://https?://', a, flags=re.I):
    return '!脏URL:' + a.split('://', 2)[2][:60].lower()
```

- `cmd_bl_mark` 见到 `!脏URL` 前缀 → **拒写并提示先修正源地址**；
- 该条脏记录已从失信库删除。

### 验证：39 条代理型 URL 不能被误伤

`https://gh-proxy.com/https://raw.githubusercontent.com/…` 这类**本来就该有两个 `://`**，
剥代理后归一成 `raw.githubusercontent.com/…`。实测 39 条（gh-proxy.com 28、ghfast.top 5、
fastgit.cc 3、gh-proxy.org 2、pz.168188.dpdns.org 1）全部未受影响。

## 六、教训

1. **「失败次数」不是失效证据，「失败原因」才是。**
   两次"因为证书过期而失败"，和两次"因为域名注销而失败"，应该得到完全不同的结论。
2. **判据别只看输入，要看"输入为什么是这个值"。**
   `code=0` 是一个把三种完全不同情况压平的抽象——压平的那一刻，信息就丢了。
3. **只进不出的列表必须有体检。**
   没有 `audit`，这 4 条误杀不会自己浮出来；它们会一直躺在那里，而且每次体检都显示"正常"。
4. **别把环境问题当成别人的问题。**
   `github.com` 主页在本网络时通时断，曾让我一度以为 20 条源被误杀；实际测活后 10 条确实不可用。
   **先证明自己的尺子准，再判别人的长度。**

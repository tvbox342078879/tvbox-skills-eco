# tvbox-janitor · 清道夫（待删收件箱）

> **一句话职责**：AI 删不掉的，全丢进**一个收件箱**，用户在那一处按单删。

## 0. 为什么存在（能力边界）

WorkBuddy 云端 space **没有删除节点 API**（`space_api.py` 只有 create / rename /
move / publish / unpublish）。所以：
- **删节点 / 删文件夹 / 删数据表** → AI 做不到，**必是人类的手**。
- **移动 / 改名 / 建节点** → AI 能做。

清道夫的招法：**用"移动"替代"删除"** —— 把该删的节点统统挪进一个收件箱文件夹，
把"删除"这件 AI 干不了的事，**降维成"打开一个文件夹、按清单删"**。

## 2. 命令

```bash
python3 janitor.py inbox                         # 建/确认收件箱（幂等）
python3 janitor.py add --node ID [--reason R]    # 移节点入收件箱 + 登记清单（AI 最后一步）
python3 janitor.py scan                          # ★ 全局递归扫描：识别所有垃圾并自动投递收件箱
python3 janitor.py scan --dry-run               # 仅预览候选（不移动），首次/安全核查用
python3 janitor.py list                          # 输出待删清单（md + csv 落盘）
python3 janitor.py restore --node ID [--target 父ID]  # ★ 误投回退：移回原位并移除清单项
python3 janitor.py census [--json]              # ★ 分层普查：一条命令回答"这块归谁管"（S158）
```

### 2.1 `census`：大生态分层普查（S158）

回答的是**治理问题**，不是清理问题：整个空间里，**哪些节点不在任何技能的责任田内**。

```bash
python3 janitor.py census           # 人读：缝的分区排名 / 责任田覆盖 / 根层级无主 / 重复组
python3 janitor.py census --json    # 机读：落盘 /workspace/S158_大生态分层普查.json
```

#### 归属真源：**两个**，不是一个

判定式只有一条：**不在任何归属来源里 = 缝**。缝不是"乱"，缝是"无主"。

归属来自两处，由 `load_territory()` 在启动时合并，**`zone_registry.json` 优先**：

| 源 | 文件 | 写法 | 谁维护 |
|---|---|---|---|
| 技能锚点 | `janitor.py` 的 `TERRITORY` | 节点 id → 技能 | 各技能自己声明 |
| 治理指派 | `ecosys-conductor/scripts/zone_registry.json` | 每区一条，见下 | 总指挥裁定 / 用户定 |

**两种挂法必须区分，挂错等于没指派：**

| 挂法 | 适用对象 | 判据 | 说明 |
|---|---|---|---|
| `node_id` | **容器型**区（如 `📁 配置·配置维护知识库`） | 整棵子树归该技能 | 进入即归属，**不再下钻** |
| `match_prefix` | **根层级散落组**（同名文档堆 ×19/×23…） | 标题前缀匹配**根层级直接子节点** | 只判一层，**不递归**，防误伤他处同名文件 |

> `match_prefix` 是 S158 补的。那批区是同一批报告散落在根层级，**根本不是容器**，
> 挂不住单个 id。当时只在 registry 里加了字段、忘了写进本文件 →
> 下一轮看 SKILL.md 的人会以为归属只认 `TERRITORY`，**文档与代码成了两套说法**。
> 那次修完缝从 315 降到 6，但**书面上没留痕**，这次补上。

**读不到 registry 时必须显式告警，不许静默降级：**
`load_territory()` 返回 `problems` 列表，census 逐条打印。缺文件时提示语写的是
> `归属只含技能锚点，治理指派的那批区会全部计为缝`（不是"没有缝"）

这是 M-R60 三态铁律：读失败 = **无法判定**，禁止折叠成"没问题"。
S158 之前正是因为没有这道告警，"表是死的"这件事被瞒了整整一轮。

- `--json` 成功落盘时**必打印「明细已落盘」**——下游 M35 检查器以此为"这次真写了"的判据。
  （census 写失败不删旧文件，旧结果还在；不设这道明示，失败长得跟成功一模一样。）

实测基线（S158 修完后）：441 节点 / 责任田 435（99%）/ **缝 6（1%）**，
剩余 3 个区待用户裁定归属（`📁 学习·Ai学习` / `📁 安全·敏感信息库` / `🌐 公众号文章归档阅读器`）。
修复前为 317（71%），差额的来源是**归属真源合并**，不是节点被删了。

### 2.2 两道收件箱护栏（G10 事故产物）

`add` 默认拒收以下两类（`--force` 可越过）：

| 拒收条件 | 理由 |
|---|---|
| 节点**非空**（有子节点） | 收件箱是待删暂存，非空容器进去就等着被整批删 |
| 空夹但名字含 `备份/backup/归档/快照/库` | **空不等于该删**——空备份夹恰恰最该留 |

> **事故背景**：实测两个备份夹 `parentId` 都指向收件箱，而 `🗄 生态备份区` total=0。
> 等于每天自动生成一批"该删的备份"，且无人会发现——收件箱本来就是等人来清的。
> `EMPTY_KEEP` 常量让 `scan` 的空夹判定同口径。

### 2.3 重复堆积默认生效

`DEFAULT_DEDUP = 2`：不传 `--dedup` 时按"同一内容 > 2 份才投递"。
原先靠人记得加参数，而**人不会记得**。

## 3. 标准流程（发现冗余 → 投递 → 用户删）

```
① 发现冗余节点（任何技能里：重复/失败/测试/废弃/过期/空文件夹）
      │
② janitor add --node <ID> --reason "<为什么该删>"   # 单节点投递（上游 file_to_janitor 亦同）
      │  → 自动 move-node 进收件箱 + 登记清单
      │
③ janitor scan                # ★ 全局兜底：从 ROOT 递归整个空间
      │  → 自动识别【废弃标记 / 空文件夹 / 重复】并**发现即自动投递**收件箱
      │  → 不给"只报告不搬"留口子——扫到即收，用户只管去箱里删
      │
④ janitor list
      │  → 生成 /workspace/S104_<MMDD>_待删清单.md（用户照单删）
      │
⑤ 用户打开「🗑 待删收件箱」文件夹，按单删，清空即完事

⑥ 误投补救：若某节点被误投（如误判的"归档表"），`janitor restore --node <ID>`
      │  → 按 add 时记录的原父节点一键移回原位，并从清单移除
      │  → 旧版清单项（无 origin 记录）可用 `--target <父ID>` 手动指定回退目标
```

## 4. 铁律

1. **只移动、不删除**：AI 无删除权，绝不假装删除（禁"我已删除"这类谎报）。
2. **不漏项**：节点不存在/移动失败 → 显式告警，清单**仍保留**该行并标"未移动"。
3. **幂等**：同 node_id 重复 add 不重复登记。
4. **状态损坏不折叠**（M-R60）：`janitor_state.json` 损坏 → 显式报错退出，不当"空收件箱"。
5. **原因必填**：每项须写清"为什么该删"，用户删前能一眼核实。
6. **全局覆盖**：`scan` 从空间超根 `gZ4xP6kXXeCpTlsH2CN9tJ` 递归（覆盖整个空间，非仅底包库根）；
   排除收件箱自身及其子树（已在箱/是箱，不扫不投）。
7. **发现即投**：`scan` 命中垃圾**直接自动投递**，不再"只报不搬"；`--dry-run` 仅用于预览核查。
8. **重复仅告警**：同目录同名重复节点只列出告警、不自动投，留人工裁决（防误删）。
9. **误投可回退**（v1.1.7）：`add` 移动前**记录原父节点**（`origin_parent`，由 `_find_parent` 全树反查；
   `node-info.parentNodeId` 不可信故不依赖）；误投用 `janitor restore --node <ID>` 一键移回原位并移除清单项。

### 垃圾判定规则（多维，覆盖"所有的垃圾"，不止空文件夹）

| 类别 | 判定 | 处置 |
|---|---|---|
| 废弃标记 | 标题命中 `KW`（废弃/已废弃/失效/作废/请删/待删/🗑/空壳/勿用/测试/重复/弃用/临时/旧版/垃圾/（旧/_old…） | 自动投递 |
| ⚠️ 例外 | 「归档」**不**判垃圾：正常业务表（如 S103「产出json·归档表」）标题常含"归档"，不视为废弃标记，保留原位 | 不投 |
| 空文件夹 | folder 无子节点 | 自动投递 |
| 空数据库 | 库记录为 0（多为清空/空壳，已多由"废弃标记"覆盖） | 自动投递 |
| 重复节点 | 同一父目录下同名 >1 | 仅告警，不投 |

> `KW` **刻意不含**「库/总库/源库」等正常词，避免误伤活跃库。

## 5. 与其他技能的联动（★ 自动投递，不是靠人喊）

**核心机制**：`core.file_to_janitor(node_id, reason)` —— 生态级联动门面，
**任何技能 import core 后一行调用**，即可把"该删但删不掉"的节点自动投递进收件箱。
永不抛异常（清理是旁路，不阻断主流程），失败仅告警。

**此外 `janitor scan` 已升级为全局自动兜底**：从空间超根递归、识别所有垃圾并发现即投递，
不再依赖上游钩子触发——任何会话跑一次 `scan` 即把全空间散落的废弃节点收拢进箱。

| 触发场景 | 上游技能 | 已埋钩子 | 动作 |
|---|---|---|---|
| 快照刷新产生旧版废弃页 | tvbox-source-hub `link.py cmd_snapshot` | ✅ | 旧快照改名后**自动投递**收件箱 |
| 建库产生重复说明文档 | tvbox-source-hub `newlib.py cmd_build` | ✅ | 重复文档**自动投递**（每次 build 都扫） |
| 底包库改名/归位留空容器 | tvbox-interface | 预留 | `file_to_janitor` 投递 |
| 失效源节点已无价值 | tvbox-source-blacklist | 预留 | `file_to_janitor` 投递 |
| 全库体检发现冗余 | legacy-watchdog | 预留 | 报出后 `file_to_janitor` 投递 |

### 联动三层（已在 hub 生态登记）

| 层 | 位置 | 内容 |
|---|---|---|
| **意图路由** | `hub manifest.json` | `待删清单/收件箱/投递/扫描` 四条意图 → `tvbox janitor *` |
| **任务链** | `hub manifest.json` chains | `清理待删节点`：scan → add → list |
| **联动契约** | `hub contracts.json` | `janitor-handoff`（任一技能 → 清道夫收件箱） |

**用法**：
```bash
tvbox janitor list          # 任一会话随时看待删清单
tvbox chain 清理待删节点     # 一键：扫描+投递+生成清单
```
```python
# 技能代码里自动投递（一行）
from core import file_to_janitor
file_to_janitor(old_node_id, '快照刷新后的旧版，已被新版取代')
```

**清道夫 = 清理动作的最后一公里**：所有技能发现的"该删但删不了"的东西，
自动收敛到这一个收件箱——**一处投递，一处删除**（用户只管去这一个文件夹删）。

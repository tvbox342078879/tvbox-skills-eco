## 10. 反面案例库（会话全程复盘，开工前必看）

### 1.1 开工前三问（防返工的核心，历史血泪换来的）

**在动手之前，必须先对齐这三件事**（§10 反面案例库证明：三次返工全因没对齐）：

| # | 问什么 | 目的 | 不問的后果 |
|---|---|---|---|
| 1 | **终点**：要整包 / 拆 lives / 只要一个可增删 json？ | 防"做完才改需求" | zoho 单：全套做完→全部撤回 |
| 2 | **概念**：这是"直播源"还是"json 配置"？先点破 | 防"做的和要的错位" | 黄蚂蚁单：做完才被问"这是能加线路的json么" |
| 3 | **可用性判据**：填进 TVBox 能跑吗？ | 防"能下载≠能用" | 天天开心单：3 张截图报错，3 轮试错 |

**只有 1 不明才问用户；2 由我主动点破；3 由我自己预检（用户视角自检）。**
**默认值**：若无明示，终点默认 = 「生成可增删 json 并入库 + 登记」。

### 10.3 具体踩坑细节

**zoho 单（返工最惨）**
- 错：默认"①②③全做"→剥csp+拆lives+入库全套 → 用户要"全部撤回+纯可用重打包"
- 改：动手前问"整包还是拆线"

**天天开心单（试错最多）**
- 错1：判定"明文直出能用"，未验相对路径主机完整性
- 错2：做了"知识库中转版"设计，才发现云盘 download_url 短时效
- 错3：中文编码**两次**→404，实测 3 次才定位
- 改：§3 相对路径必探；§4 中文不编码；§1.2 交付自检

**黄蚂蚁单（提速但概念未对齐）**
- 错：一把梭做完，用户才问"这是能加线路的 json 么"
- 改：§1.1 第二问 —— 开工第一句点破"这是源还是配置"

### 10.2 三次返工根因（核心教训）

```
阶段一(#5): 做完 → 用户改需求 → 返工     (缺: 事前确认终点)
阶段二(#15): 交付 → 用户跑不通 → 返工     (缺: 事中可用性验证)
阶段三(#16): 做完 → 用户概念错位 → 澄清   (缺: 事前概念对齐)
```

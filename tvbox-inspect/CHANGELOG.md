## v1.3.31 — 报告改覆盖模式：从源头制止云端副本堆积

### 起象：资料库顶层堆了 41 份同名文档
用户原话：「没看到收件箱，整理下，乱七八糟」。实测（2026-10-20，`list-nodes --parent-node-id ""`）：

| 标题 | 份数 | 体积跨度 |
|---|---|---|
| 生态1015_遗留问题监测报告 | 19 | 11.1KB → 42.7KB |
| 生态遗留趋势留档（跨设备） | 14 | 2.5KB → 32.7KB |
| 生态1016_遗留问题监测报告 | 8 | 43.5KB → 44.9KB |

41 份 MD5 **各不相同**、体积逐个变大——不是复制粘贴的副本，是**同一份文档被反复
"新建"堆积**。根因不在 `create_doc.py`（它本就支持覆盖），而在 `_upload_report()`：

```python
# 修前：无条件新建
r = subprocess.run(['python3', script, '--title', title, '--content-file', path], ...)
```

而两处锚点文件（`trend_node.json` / `last_report_node.json`）**一直在写、从来没读**。
`cmd_trend_upload` 的 docstring 甚至写着「node id 存 trend_node.json」——
存了，但没人用。注释里那句「便于下次覆盖同节点」是**承诺了没兑现**。

### 修
`_upload_report(path, title, node_id=None)` 增加第三种参形态：

```python
if node_id:
    cmd += ['--node-block-id', str(node_id), '--space-id', SPACE_ID,
            '--confirm-overwrite']
```

三处调用点各自读自己的锚点：

| 调用点 | 锚点 | 策略 |
|---|---|---|
| `cmd_trend_upload` | `trend_node.json: node_id` | 有则覆盖，永远只有一份 |
| `report --upload`（报告正文） | `last_report_node.json: latest` | **同日重跑覆盖当天那份**；跨日新建 |
| `report --upload`（趋势同步） | `trend_node.json: node_id` | 同趋势上传 |

新增 `_read_anchor(fname, key)`：文件缺失/损坏 → 返回 `None` → 调用方按新建处理。
**覆盖失败不降级为新建**（否则又变回堆积）。

### 两个坑（都是实测撞出来的）
1. **`create_doc.py` 有护栏**：全量覆盖必须显式传 `--confirm-overwrite`，否则报
   `全量覆盖文档前必须取得用户明确确认`。我第一次改完就漏了这个参数，
   实测 `ok=False`，覆盖率 0。护栏是对的——但说明「覆盖」不是传个 id 就完事。
2. **报告锚点不能无条件覆盖**：`last_report_node.json` 若跨日还覆盖，就会把
   昨天那份改成今天的内容。所以必须比 `title`（含日期戳），标题变了才另起一份。

### 实测证据
```
覆盖前 32709B → 覆盖后 344B, node_id 保持 tHmr5meQ44y34ksSCD3Gfe ✅
连续两次上传: 第1次 node=...CD3Gfe / 第2次 node=...CD3Gfe（同一节点）
无锚点上传:   ok=True 新建 YlP6g2QLSx73BVQxpvYBu4（测试副本已入收件箱）
```

### 存量处置
已堆积的 38 份历史版本（保留每组最新 1 份）移入顶层
`🗑 历史待删（旧版本·确认后可整夹删）`，按标题分 3 个子夹。用户可整夹删；
需要时重新生成放回即可。资料库顶层从 **67 → 15**。

## v1.3.30 — M16 判据修：已结条目的历史叙述不是流程步骤

### 起象：终验判据④ 每轮红一次

```
    遗留: 1 条悬空命令引用

```
`tvbox inspect jobs` 确实不存在（实测 `invalid choice: 'jobs'`）。但报出来的这条不是流程步骤——
`tvbox-inspect/scripts/flow.json` 里躺着的是：

> `[已清零 2026-10-20]（sid=b990c7ef334c）M45 已补判据并实测：tvbox jobs 实测 4 个任务全部启用、停用 0 个…`

这是在**记录当初查过 `tvbox jobs`**，不是让人照着跑的一步。M16 的原实现把整个 `flow.json`
`json.dumps` 完拿正则一扫，已结欠账里的历史叙述和活动流程步骤在文本上长得一模一样，
于是每轮都把它当成一条悬空引用报出来。

### 修
扫描前先剔除「已结条目」的字符串值，键一律保留：
```python
def _strip_done(o):
    if isinstance(o, dict):
        return {k: _strip_done(v) for k, v in o.items()}
    if isinstance(o, list):
        return [_strip_done(v) for v in o
                if not (isinstance(v, str) and not _backlog_is_open(v))]
    if isinstance(o, str):
        return '' if not _backlog_is_open(o) else o
    return o
```
复用已有的 `_backlog_is_open` 判已结，不另造词表（M-R38 单一事实源）。

### 中途修错一次，记下来
第一版把**键也剔了**，判据还写反了：
```python
return {k: _strip_done(v) for k, v in o.items() if not _backlog_is_open(k)}
```
`_backlog_is_open(x) == True` 意思是 **x 未结**。写成 `not ...` 才保留，等于"保留的恰好是已结的"。

实测后果：10 个技能的 flow.json 命令引用从 **68 条被剔到 0 条**，连我人造的
`tvbox inspect zzznonexist` 都留不下来——**检查器被修成了哑巴**，而且它还会打印 ✅。
这是我这一轮最该防的失败形态：为了让一条假红变绿，把真红的能力一起关掉了。

修订后复验：

| | 剔除前 | 剔除后 |
|---|---|---|
| 命令引用总数 | 68 | **59** |
| 剔掉的 | — | 9 条（全在已结条目里） |
| 人造悬空引用是否保留 | — | **是** |

### 判据
- `tvbox inspect scan` → ✅ 无遗留
- 剔掉的 9 条仍可追溯：原条目在 flow.json 里，只是不参与"会被执行"的扫描

## v1.3.28 — 新检查器 M42（外置索引断链）+ 修 scan 退出码恒 0

### ① 新检查器：外置索引断链（M42 / check=`link_break`）

**起因是查体积时顺手扫了一眼索引，扫出一处骗了好几轮的东西**：
`tvbox-source-hub` §4.5 自 v1.0.46 起就写着「依据与踩坑全文见
`references/concurrency_M-R114.md`」——**那个文件从来没被创建过**。

v1.0.46 的 CHANGELOG 写着外置产出是 `eco_unified_entry.md`（13694B）+
`manual_外置细则.md`（10293B），**根本没有第三个文件**。于是正文指向了一个不存在的正本，
横跨多个会话无人发现。危害是双向的：

- 读者按图索骥 → 扑空；
- AI 看到「已有正本」→ 不再深究，直接引用一个空地址。

比体积超标隐蔽得多，因为 `docsync` 原来的 5 项查的全是「数字对不对、库 id 废没废」，
**从没查过「这个文件在不在」**。

判据两种写法都查：`[..](references/x.md)` 与反引号 `` `references/x.md` ``。
后者不渲染成链接，任何链接检查器都发现不了——这次漏掉的恰是这一种。

**实现只写一份**：抽 `find_link_breaks()`，`cmd_docsync` 第 6 项与 `check_link_break`
共用。初版把逻辑直接写进 docsync，后来登记 M42 时差点在 CHECKERS 里再抄一遍，
那正是「同一判据两处抄，抄完必漂移」。

**受控实证**：注入 `references/不存在的探针文件.md` → docsync 报 1/27 断链、drift=1、rc=1；
`inspect scan` 报 M42 一条耗时遗留；撤掉 → 26 处全绿、drift=0、rc=0。

顺带补齐 `tvbox-source-hub/references/concurrency_M-R114.md` 正本（五条判据原文、
四条档位理由、23处/10文件→75文件迁移实况、两个迁移才暴露的 bug），
文中每个事实都对过 `concurrency.py` 原文与 CHANGELOG，不是据记忆重写。

### ② 修 scan 退出码：同一命令三个入口三个答案

查 M42 能不能当门禁时发现，注入断链后：

| 入口 | 退出码 |
|---|---|
| `inspect_engine.py scan` | 0 |
| `inspect.py scan` | 1 |
| `tvbox inspect scan` | **0** |
| `tvbox inspect scan --strict-exit` | **0** |

根因两层，都在「返回值→退出码」这道归一上：

- `inspect_engine.dispatch` 的 `__main__` 写 `dispatch(...)`，返回值丢掉 → 恒 0；
- `tvbox._as_exit_code` 只认 `int`（`bool` 映射成码），`cmd_scan` 返回的是
  **findings 列表**（数据）→ 一律归 0。于是「有 1 项耗时遗留」经 tvbox 跑出来是成功。

修法**只动 CLI 出口，不改 `cmd_scan` 的返回值**：引擎内部有 4 处
（report/diff/trend/aging）拿它当 findings 用，改数据结构会连带打断它们。
在 dispatch 分支做 `return 1 if _f else 0`，`__main__` 补 `sys.exit(...)`。

修后四路一致：**注入态 1/1/1/1，干净态 0/0/0/0**。

### ③ 教训

> 一个**只报绿不报红**的检查器，比没有检查器更坏。
> `docsync` 报了十几个会话的「一致」，而它检查的是文档**内容对不对**，
> 从没检查过文档**指向的东西存不存在**——覆盖面缺口伪装成健康度满分（M-R113 的另一面）。
> 补完缺口后立刻要问第二个问题：**新检查器报出来的东西，能不能当门禁？**
> 这次答案是不能，因为退出码在最后一层被归一成 0。

## v1.3.17 — 进化停滞维度改信「磁盘事实」：台账是手填副本，会静默过期（S158 七补）

### 一、事故：M19 报的 2.1 天是假数

用户点第 2 件事，查下去发现 **M19 拿断掉的记录下结论**。

| 证据 | 值 |
|---|---|
| 台账 `末次升级` | `2026-10-16T12:00:00Z` |
| 该值形态 | **整点、分秒皆 00，12 条台账里唯一一个** → 手填占位 |
| `evolution_log` 该技能最后一条 | `2026-10-16T00:18:47Z`（1.20.1） |
| 实际 SKILL.md mtime | **2026-10-18 20:09**（v1.34.3） |

从 1.20.1 到 1.34.3，**14 个大版本，两条登记途径一条都没记**。
而 `末次升级` 全仓唯一写入点是 conductor 的升级入口 ——
**任何技能绕过入口直接改版本，台账必然停在旧值**，检测器却照此判"停滞"。

> 这不是"技能进化慢"，是"测量工具测的是一个没人维护的副本"。

### 二、为什么第一版修法没生效

第一版只加了「台账 version ≠ 磁盘 version → 采信 mtime」。
实测**没触发**：台账 version 早就被回填成 `1.34.3` 了，
**版本记对了、时间没改** —— 只比 version 永远抓不到。

### 三、最终判据（两条路）

| 情形 | 判据 | 采信 |
|---|---|---|
| ① 版本漂移 | 台账 version ≠ 磁盘 version | 磁盘 mtime |
| ② 时间滞后 | mtime 比台账晚 **>12h**（`_MT_SLACK`） | 磁盘 mtime |

证据里写明 `来源=台账 / 进化留痕 / 磁盘mtime（…佐证）`，
**不许把三种来源混成一个数字**，否则出问题无法归因。

### 四、为什么不无脑取 max

mtime 会被 `git checkout` / 批量 `sed` / `cp -r` 刷新，不代表内容真变了。
故只在**台账已有记录且 mtime 更新**时单向采信；
伪造一个「5 天前 mtime + 今天台账」的技能实测 → **不触发**，旧文件不会被当新鲜。

### 五、反例验证

| 目录不存在 | `(None, None)` 三态 | ✅ |
| 5 天前 mtime + 今天台账 | 不采信 mtime | ✅ |
| 账龄 2.5/5.0 天 | 仍判停滞（35/10 分） | ✅ 曲线未改松 |

此前 19 类检查器全都在**各技能自己的库和 /workspace 文件**里打转。

`check_eco_gap`：调 `janitor census --json`，按「缝节点占比」报。

### 二、故障注入抓到检查器自身的两处缺陷（这轮最值钱）

**缺陷1：配置读失败被静默折叠成默认值**

```python
# 原：
try:
    cfg = load_monitors(); thr = float(cfg['gap_threshold'])
except Exception:
    pass                      # ← 配置坏了，用 0.60 继续跑，毫无痕迹
```

改为：读失败落到「无法判定」并在 item 里注明 `（gap_threshold 未取到：XxxError，退回默认 60%）`
——**降级允许，装没事不允许**（M-R60）。

**缺陷2：读外部文件前不看"这次真的写了没"**

`census` 写失败时**不删旧文件**，旧结果还在。于是注入"落盘缺失"时，
检查器照样报出 72% 真阳性——**看起来在正常工作，其实用的是上次的数据**。
这是"依赖外部文件"的通病：失败不产生新文件，而旧文件还在，失败长得跟成功一模一样。

修法：census 成功落盘才打印「明细已落盘」，检查器以这句话为前置判据。

## v1.3.5 — M09 判据与执行器不同口径（S151）

### 现象

清账 M09 僵尸源时报 188 项「已命中失效库拉黑，但源库状态仍为待查」。

抽查后发现**其中 27 项是检查器自己造的假红**：拦截器 `blk check` 对这些源
返回 ✅ 放行，M09 却报「你没停用」。工具之间互相矛盾。

### 根因

M09 的判据是「失效库表里有这个 host，就算命中」：

```python
dead_hosts = {host for r in dead if 拉黑范围.startswith('整域')}
archived = api in dead_api or (h and h in dead_hosts)
```

但拦截器的判据**不是**这个——S026（代理域）和 S151（平台域）都要求这两类域
**永不参与整域拉黑**，拦截器在读侧把它们滤掉了。

于是：**执行器放行，检查器报"僵尸源"。** 同一份数据，两套判据，各说各话。

### 修法

M09 的 `dead_hosts` 套同一套过滤：

```python
dead_hosts = {h for h in dead_hosts if not _is_platform_host(h) and not _is_proxy_host(h)}
```

同时新增 `_is_platform_host` / `_is_proxy_host`（纯域名口径），与 `blk.py` 的
`is_platform_host` / `is_proxy_host` 对齐。**复制实现而非 import**，保持监测中立
（不依赖被监测技能的可导入性），但判据必须一致。

### 结果

| | 修前 | 修后 |
|---|---|---|
| 报出项 | 188 | 158 |
| 其中假红 | 27（代理域被降级后残留的整域误判） | 0 |
| 真实欠账 | — | **158** |

剩下的 158 项是**真欠账**：源库 801 条全部标「待查」，其中 158 条确实已命中
单条拉黑（多为代理 URL 原文精确匹配）。这属数据处置（回填源库状态），
**不在本检查器职责内，也不擅自动手** —— 由用户决定。

### 教训

> **检查器和执行器用的是两套判据，就一定会打架。**
> 「谁对」不是关键——关键是两边都在报，人就分不清哪条是真欠账。
> 判据的单一事实源必须沉到能被两边共同引用的地方（此处是 `_is_platform_host`
> 等判据函数），而不是各自 `if` 里重写一遍。

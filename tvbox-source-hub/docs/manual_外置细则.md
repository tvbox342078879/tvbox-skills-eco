### 8.3b ★ 内容分级三档（规则 56 · 全量/纯净/18 · S102）

> 用户 2026-10-16："有些站在分类里面有伦理片……**全量的是保留伦理片的，纯净的是伦理片隐藏的，
> 18是只保留伦理片这个分类的**……收到我说做全量版时用全部分类都有的，做纯净版只能用没有18的，
> 做18版只用只有伦理这个分类的。"

**判据源**：站点 json 的 `sites[].categories`（站点内部内容分类数组，**不是** `分组类目`/`可用体系`）。

| 内容分级 | 判定 | 含义 |
|---|---|---|
| **全量** | 有18分类 **且** 有非18分类 | 混编站（如西瓜：30分类含1个伦理片） |
| **纯净** | 有分类且**无**任一18命中 | 无18内容 |
| **18** | 有18分类 **且全**是18分类 | 纯18站（如 🔞 那批） |
| **未知** | 无 categories / 空数组 | **未确认≠干净**，出纯净版**不收** |

**词表**（`link.ADULT_WORDS`，子串匹配）：
`伦理 · 三级 · 激情 · 成人 · 18禁 · 里番 · 无码 · H漫 · 情色 · 禁片`
> ⚠️ 严禁收地域/泛词（`欧美/日韩/港台/韩国/日本/动漫/福利`）——实证：正常站有 `日韩动漫`
> 分类，收地域词会把干净站误判成18。

**入库**：`ingest` 自动读候选的 `内容分类` 字段算分级，写 DB_SRC 两列
（`内容分级`select / `内容分类`text）。无 categories → `未知`。

**出库（用户说"做X版"时执行）**：
```bash
link.py export --level all   --out 全量版.json   # 取"全量"标签（分类全留）
link.py export --level pure  --out 纯净版.json   # 取"纯净"标签（铁律：未知/全量都不进）
link.py export --level adult --out 18版.json     # 取"18"标签（只留18分类）
link.py grade --candidates <站点包.json>          # 打标预览（不改库）
link.py tag-backfill --dry                        # 老数据回填预览（无categories→未知）
link.py baksync                                   # 备用库补同步（S129 P010）：SRC→BAK按host差集补写；ingest成功后自动触发，可独立手动跑（幂等）
```

**纯净版铁律**：只有 `纯净` 标签进纯净版；`未知` 与 `全量` **一律不收**（防漏网18源）。
**老数据**：源库 1221 条无 categories，回填只能标 `未知`（**绝不瞎猜**）；本规则只管新入库。
**同 api 多站名**：`classify_adult_from_sites` 取**最保守**（任一站有18 → 整 api 判18）。

### 8.14 ★ 在线包对比分析套路（轻量化溯源 · v1.0.10）
> 场景：用户给「在线接口 + 轻量化成品」，要求做原版 vs 轻量版多维对比/溯源表。

**在线 JSON 解析三连坑（2026-10-15 box 原版实测）**：
1. `//` 注释行（TVBox 惯例）→ 先剥行（L019 套路）
2. `####` 前缀 = TVBox 注释语法（作者禁用的键，如 box 原版 `####"spider"`）→ 剥前缀再解析，**并留意双 spider 键**（原版文件可能 #### 在线地址 + 本地地址并存，Python json 取后者）
3. `,ext"` 缺引号等手工编辑瑕疵 → 正则 `,(\w+)":` → `,"\1":` 补全后重试
4. **解析成功后必须交叉核对**：站点数 vs spider md5 在线下载实测值 vs 索引文档登记值（三者可能因作者静默更新而互不一致，如 easy999 easy1012.png→easy10.15.png）

**集合比对失真坑**：站点名分隔符风格不统一（qist 仓库版 `123 • 云盘` vs 定制版 `123｜4K`）→ 直接集合比对 87/164 命中，**规范化分隔符（`[•｜|]`→`|`）后**才能还原真实同源关系；同源结论要 api 级交叉验证（jsm 在线版 api 与 qist 仓库版交集 64）

**轻量化对比五步法**：①原版/轻量版/源候选三件下载 → ②spider jar md5 硬比对（判体系，规则53）→ ③站点 key 级增删 + api/ext 差异 → ④配置模块矩阵（spider/sites/lives/parses/rules/ads/flags/doh/ijk/wallpaper/logo/warningText）→ ⑤复刻途径按「被删项完整配置可直接抄回」组织交付

**台账 select 枚举约束**：③台账「触发类型」仅 6 选项（新接口处理/整包入库/扫描归源库/规则维护/查询答疑/纠错返工），「反哺状态」4 选项（已闭环/已同步源库/已同步底包/待同步）——数据表交付类记「整包入库」+「已同步底包」

### 8.16 ★ 写后验证双保险 + 成长协议自举（v1.0.12 · S020 全局复盘）
> 场景：一切"写库→读回核对"动作；SOP 成长协议自身的可信度维护。

**写后验证信号分级（S020 实证：验证机制本身会撒谎）**：
1. **进程内读回**（rows_of/读回验证）：快但可能命中缓存旧值——`invalidate(db)` 必须**双清**（db 键 + args 含该 db_id 的 api 层键，core.py S020 已修，历史同症状二次复发：首次绕过 core 未 invalidate，二次 invalidate 漏 api 键）
2. **短重试 3 次**（0.6s 间隔）：防服务端写入延迟（cmd_log/lib-log S020 已内置）
3. **独立进程复核**（新起 python 跑 get_database_content）：前两级都报"未查到"时的终审——**禁信单一进程内信号**（S019 实测：进程内报未查到，独立读回证实记录已在库）

**成长协议自举（用 SOP 管 SOP 自己的经验）**：SOP 自身的坑也走 add-case→promote 流水线（S020 实证：promote 半拉子缺陷/缓存伪信号/④库漏落全部按标准协议登记，SY19 即为自举产物）；`check` 的 🔥高频出处（≥3 次）= 下一轮提炼脚本/规则的输入。

**复盘双库对账（S020 补的铁律）**：S10 复盘闭环时③台账与④库**各落各的**——③按任务类型（tvbox log）、④按操作类型（tvbox lib-log）；本次任务踩到平台操作坑（记录读写/上传/表格/节点/分页/字段）就**必须**落④，漏落=复盘不完整（实证：S018/S019 平台坑曾只进 CHANGELOG/SOP，④库停更 3 小时）。

**症状 alias 维护（S021 校准实证）**：新增/改写症状时同步补 alias（口语化变体），并重跑校准集（19 症状×2 变体+负样本，四指标：正确/错配/漏报/误报）；权威源 `growth.route_calibration` 记录定标依据。口语化查不到的根因十有八九是 alias 缺失，不是阈值问题。

### 8.6 ★ 技能↔脚本联动 + 并行加速（提效双引擎 · 规则 45/48）

**① 联动**：`link.py`/`blk.py`/`evolve.py` 共享同一 `core.py` 实例 → 进程内缓存（`rows_of`/`api` 读缓存、写后 `invalidate`）+ `fanout` 并发读 + 限流写；`tvbox run` 同进程串联多命令缓存全局复用；`manifest.json` 把「意图→命令」显式绑定（`tvbox manifest` 可查）。

**② 并行**：脚本内 `collect/status/brief` 由串行 7 读改 `fanout` 一轮，`snapshot` 10 路读并发；跨命令 `tvbox p "a" "b" "c"` 用**子进程隔离**并发（避开多线程 `sys.stdout` 缓冲串扰）。

**实测**（2026-10-15 同环境）：`status` 串行 7 读 → fanout ≈0.38s；`run brief status` 0.85s → 0.4s（≈2×）；`p` 三命令 0.9s → 0.4s（≈3×）。

> **约束**：写路径 `add_records` 仍串行保 QPS（每批 100 + `sleep 0.4`）；大批量可用 `add_records_parallel`（workers=3）限流并发。

### 8.10 ★ 端到端完整流程（正本在 flow.json，本节仅索引）

> **机器可读正本**：`scripts/flow.json` —— 含 `route_decision`（四路分流）/`steps`（0~10 十一步，含规则·命令·产物）/`iron_order`/`self_check`（13 项收尾清单）/`snapshot_refresh_rule`/`backlog`。
> 禁在此抄第二份（M-R38 单一事实源：抄本必漂移）。**开工前查流程 → 读 flow.json**，改动只改 flow.json。

**只能背下来的三条铁律**（checklist 在 flow.json，这三条是不查也不会错的）：
1. **顺序不可乱**：触发 → 体系识别 → 拆解 → 黑名单拦截 → 去重 → 测活 → 入库 → 交付四项 → 复盘四问。黑名单拦截**必须先于**去重/入库；复盘**必须当场**，不拖下个任务。
2. **快照刷新判据**：凡对源库/失效库的**写操作**（ingest 新增/状态回填/block 归档）收工必 `tvbox snapshot`；纯规则/命名/文档变更**不刷**，须在复盘说明未刷原因。
3. **体系判不出 → 标「待确认」**，交付时显式列清单请用户拍板（范式：ygd/peek1/天天开心 9 文件），**禁自动猜**。

### 8.17 ★ 全局联动生态·四化（规则 54 · 正本见总册/注册表）

> 用户原话："实现流程标准化，标准流程化，任务效率化，联动生态化的全局性生态。"

| 四化 | 判定（不满足即不合格） | 落点 |
|---|---|---|
| 流程标准化 | 自建技能 = `version` + `CHANGELOG` + `flow.json` 三件套，缺一 evolve scan 不过 | library 随官方不强制 |

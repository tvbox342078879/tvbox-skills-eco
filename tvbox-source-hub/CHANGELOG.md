## v1.0.52 — 快照旧页回收通路补齐（S158·G4 单向棘轮）

### 问题：快照只进不出

`link.py` 每次刷新快照都会在 `📁 数据·数据源总库` 生成新页，旧页留在原地。
「产生通路」是自动的（刷新即新建），「回收通路」却要**人想起来去删**——
**而人不会想起来**。这正是本轮归纳的缺陷模式之一：**单向棘轮**
（只装不卸、只建不拆、只写不读），它不会报错，只会让库慢慢变重。

### 修改

1. **`SNAP_PARENT` 提为常量**（原为裸写字面量散在调用处）——
   M-R85 单一事实源：跨函数复用的标识符必须从正一点派生，手抄字面量迟早抄错。
2. **旧页自动投递到清道夫收件箱**：刷新成功后，把被取代的旧版文件投给
   `tvbox-janitor`（`file_to_janitor`），附原因「快照刷新后的旧版（stamp），已被新快照取代」。
3. **投递失败必须显式报警**，不许静默：

```
→ 已自动移入「🗑 待删收件箱」（清道夫），无需手动找
```
失败时：
```
⚠️ 旧快照**未投递成功**（仍在 GHqCfbGoCOAOV4g4NVxsCE 原地）——
   这类残留会越积越多，请人工清一次或查清道夫收件箱是否可用
```

第 3 点是关键：**回收动作失败不能长得跟没发生一样**。
一个"可选的成功"在工程上等于"必然的失败"——因为没人会去查它到底成没成。

## v1.0.49 — 修正 jar 字段语义 + 体系判定（两处都是"想当然"留下的）

承接 v1.0.48。上一版把 `build.py` 接进真库后，`jar地址` 仍是 0/620，顺着查下去发现了两个更深的问题。

### ① `jar文件名` 与 `jar依赖` 在 241 行上逐字相同

两个字段存的都是 `mojiGuard.jar` / `amns.jar`，等于其中一个白存。
根因在 `backfill_jar.py`：同一个 `jar` 变量同时写进两个字段。

改成分工：

| 字段 | 存什么 | 回答 |
|---|---|---|
| `jar依赖` | `是` / `否` | 要不要带 jar（**筛选层**）|
| `jar文件名` | `mojiGuard.jar` / `amns.jar` | 带哪个（**取用层**）|

两个字段都存文件名时，出包的第一层筛选取不到值——这才是重复的危害，不只是冗余。

**实测分布（620 行，零矛盾）**

| `jar依赖` | `jar文件名` | 条数 |
|---|---|---|
| 否 | 空 | 112 |
| 是 | 有 | 241 |
| 是 | 空 | 267（依赖 jar，未知是哪个 → 待验）|

### ② 差点第二次踩同一个坑，这次做成了机械闸门

改字段时顺手写成 `{'select': '是'}`，而 `jar依赖` 的 schema 是 **text**。
平台照样整条拒绝，错误码还是那个把"字段不存在"和"类型不对"混在一起的
`invalid fields ... failed to parse` —— v1.0.48 刚记过一次，转头就要再犯一次。

所以规则光写进文档不够（M-R107：纪律要设在数据流必经点），加了
`backfill_jar.py::type_gate()`：**逐字段比对 `{type: value}` 的键与 schema**，
不符就中止整批。预演也过闸门。三条用例实跑验证：

```
用例1 select 写 text 字段 → 拦
用例2 类型正确          → 放
用例3 幽灵字段          → 拦
```

### ③ `classify()` 把本地 py/js 误判成 jar系

7 条本地线路（`./py/*.py` × 6、`./lib/drpy2.min.js` × 1）被判 jar系，理由是"要有引擎 jar 才跑"。
这条推理把**引擎**当成了**外部业务 jar 依赖**：

- `jar系` = 出包必须带某个外部业务 jar，不带就起不来
- 本地 py/js = 靠 py 引擎（drpy2 / TVB-py）执行，与 jar 依赖无关 → **直链系**

反向验证站得住：`jar_file()` 认得出 jar 家族的 241 条，**恰好等于**库里有 jar 的 241 条，一条不差。

> 期间我一度走偏：以为 `csp_PanUC`/`csp_Config` 是"标准类、不需 jar"。
> 库里 `测活证据` 写得很清楚——「csp类线：依赖 jar，仅可随底包端测」。
> **标准 jar 也是 jar**，csp 一律保持 jar系。方案因此从"改 274 条"收窄到"只改 7 条"。

修正后：`直链系 112 / jar系 508`，全表 620 行与 `classify()` **零偏差**。
新增 `scripts/backfill_system.py`（默认预演，`--apply` 才写）。

### ④ 结论：`jar地址` 是结构性缺口，不是漏填

全生态 4 个库（台账/经验库/生态登记/失效源库）**没有任何 jar 地址数据源**；
源数据里只有文件名，没有下载地址。要补必须从配置包解析下载地址，是另一个量级的工程。
**本轮不装作能修**，如实记在这里，等真要用时单独立项。

## v1.0.48 — 出包闭环接线 `build.py`（跑通真实入库）

承接 v1.0.47。上版四禁只解决了"不许拖"，但 `build.py` 本身是个 67 行的半成品：
只写 `/tmp` 不入库，规范化和分类逻辑是凭记忆写的。本次接到真库上，代价是一串真实报错。

### ① 最关键的一个坑：字段名和枚举值都不能凭记忆写

真实报错（`batch_add_database_records.py` 原文）：

```json
{"success": false, "error": "invalid fields (not found in schema or failed to parse): [体系 入库时间 源类型]"}
```

三件事同时发生：

| 字段 | 问题 | 正解 |
|---|---|---|
| `入库时间` | **schema 里根本没有这个字段** | 删掉（时间维度由 `生产时间` 承载） |
| `源类型` | 我写的值是 `py` / `java`，schema 只有 `py线路` / `csp线路` | 改用合法枚举 |
| `体系` | 字段存在，但值必须落在 `jar系` / `直链系` 内 | 校验后才写 |

注意 `体系` 字段名是存在的，却被判 `not found in schema or **failed to parse**` ——
**select 值不在 options 内，和字段不存在返回同一个错误码**。
靠猜字段名 + 猜枚举的写法，必然一次次撞墙，而报错信息不会告诉你哪个是哪种。

**改为 schema 驱动**：新增 `schema_of(db)` 直接读 `get_database_schema.py`，
`normalize()` 只写 schema 里真实存在的字段，且 select 值必须命中 options，
不合法就丢弃该字段并打印告警（不整条丢、也不硬塞）。schema 读不到就
**放弃本次入库**——不赌运气。

## 2026-10-16 v1.0.27 云端节点读取语义三态：结构失配 ≠ 空库（S086·M-R60）

## 2026-10-16 v1.0.26 读表基座三态化：消除"假空表"与缓存毒化（S083·M-R60）

## 2026-10-16 v1.0.25 云端读取三态化：拒绝假权威快照（S082·M-R60）

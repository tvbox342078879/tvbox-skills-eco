# TVBox 数据源总库 Hub

> **职责边界**：`tvbox-interface` 管**整包**（成品包、底包、体系分类）；本技能管**线路**（单条数据源、可跨包复用的元素）。
> 一个包处理完 → `tvbox-interface` 产出成品包名 → **本技能把它的每条有效线路拆进源总库**。两者都要做，缺一不可。

### 为什么是两库，不是三库（S160 决策依据）

三库是**按技术形态切库**（py 一库 / csp 一库 / 实测成品一库），代价有两个，都在 S159 现形：

1. **字段定义各自为政**——同名 `可用体系`，csp 库是 `select` 单选、成品库选项装的是旧体系名，
   与 py 库的 `multi_select + A/B/C/D/🔞` 完全不是一套，跨库统计直接失真。
2. **落点要靠猜**——「这条线路进哪个库」取决于 api 前缀，判据写错过一次（csp 源灌进成品库）。

S160 改为：**技术形态写进字段（`源类型`），不写进库结构**。一条线路只存一份，
库只按**用途**分（线路待用 vs 成品可进包），这正是 M-R103「一条线路只存在于一个分组」的更细表达。

### 两库是**互斥分区**，不是备份

S160 迁移实测：两库 api 集合**交集 = 0**，合计 729 条 api 全局唯一（729/729）。
**切勿把两库当副本互相同步**，也别把两库拼起来当"去重前"再 count——那会造出一批假重复。

### 落库判据（唯一实现在 `link.dest_db()`）

| api 形态 | 落点 | `源类型` 值 |
|---|---|---|
| `csp_*` | 线路源库 | `csp线路` |
| 其余（`http*` / `./py/*`） | 线路源库 | `py线路` |
| — | **成品源库不由线路入库写入**，由 `probe harvest promote` 从实测通过的源提升 | — |

> S160 起 `dest_db()` 是常量返回（只剩一个线路落点）；`src_type(api)` 是配套的形态判据，
> 两者共用"是否 `csp_` 开头"这**一把尺子**，不会各算各的。

## 2. ★ 核心规律：「后缀即体系」（硬数据，不是猜）

> **实测验证**：库内 `guard系` 95 条 **全部**带 `Guard` 后缀；`lytvs系` 76 条 **全部**不带。交叉违规 = 0。
> 价值：把体系识别从"下载 spider → 解 dex"（慢、重）降到"**看字符串后缀**"（即时）。

| api 形态 | 判据 | 可用体系 | 依赖 |
|---|---|---|---|
| `http(s)://...` | 采集接口/直播源/远程 js·py/远程 json | **A+B+C+D 全系** | **零 jar，跨系通用** |
| `csp_XxxGuard` | 带 Guard 后缀 | **B** | moji 加壳 spider |
| `csp_XxxAmns` | 带 Amns 后缀 | **D** | Amns 系 spider |
| `csp_Xxx`（裸类名） | 无上述后缀 | **A** | 标准 dex spider |
| `./` `../` 相对路径 | 依赖作者资源包 | **不入库（判死）** | 已随作者离线失效 |

> 🔞 是**正交的内容维度**：源本身是成人内容则**额外勾选 🔞**，与 A/B/C/D 并存，不互斥。

## 4.5 ★ 并发铁律 M-R114（S110 — 只准跑 `concurrency.run_bounded`）

**跨任务不许并行，条目级才许并行。** `batch_update` 提交的是**整条 properties**，
不是字段级合并，所以后写的会把先写的整条覆盖 —— S110 实测三任务同时写同批记录，
`reclass2` 跑 4 分钟一条没落库，同时质量评测在改同一批行。

| 场景 | 对 | 原因 |
|---|---|---|
| 三任务同时跑，都写两库 | ❌ | 写集合相交，整条覆盖 |
| 一任务内 111 条记录并发评测 | ✅ | `record_id` 各异，写集合不相交 |
| 并行读、串行写 | ⚠️ | 读可并行，写仍须串行（M-R35） |

**档位表（禁就地拍数）**：**A** 自家 API=8 ｜ **B** 公网站点=6 ｜ **C** CDN 分片=4 ｜ **D** 本地=min(核,8)。
超上限 **raise 不静默截断**。五条判据原文、档位理由、迁移实况、两个迁移才暴露的 bug，
正本见 [`references/concurrency_M-R114.md`](references/concurrency_M-R114.md)。

from concurrency import run_bounded, TIER_WEB
rep = run_bounded(rows, work, tier=TIER_WEB, workers=6, label='质量评测',

## 4.7 ★ 写库三铁律（`build.py` 已固化）

S111 接真库时，一次"只猜到失败 1 条"的排查暴露出写库的三个必踩点。**三条都不是文档纪律，是代码卡**。

**① 字段名和枚举值都不许凭记忆写 —— 先读 schema**

```
{"success": false, "error": "invalid fields (not found in schema or failed to parse): [体系 入库时间 源类型]"}
```

`体系` 字段名明明存在却被判非法：**select 值不在 options 内，和字段不存在返回同一个错误码**。
报错只列字段名，不区分是哪种，靠猜必然反复撞墙。

- 一律走 `schema_of(db)`（底层 `get_database_schema.py`）拿真实字段与 options
- select 值必须命中 options，否则丢弃该字段并告警；**schema 读不到就不写库**，不赌
- 存量校准值（线路源库）：`源类型` 只有 `py线路`/`csp线路`，**没有** `入库时间` 字段

**② 每个字段必须是 `{type: value}` 的 dict**

`_db_types.validate_properties` 遇到任何非 dict 值就 `return {}`，整条记录判"校验后为空"。
而 `add_records` 拿不到 `results` 时返回 `(0,0)` —— 看起来像"成功0失败0"，实则**根本没写**。
入参预检必须做，别让记录静默消失。

**③ 字段的类型键也必须查 schema，不能只看字段名**

同一天第二次踩：改 `jar依赖` 时顺手写成 `{'select': '是'}`，而该字段 schema 是 **text**。
平台照样整条拒绝，错误码还是那个混在一起的 `invalid fields ... failed to parse`。

现在 `backfill_jar.py::type_gate()` 把它卡死：**逐字段比对 `{type: value}` 的键与 schema**，
不符就中止整批、列出问题，一条都不发。预演（`--dry`）也过闸门，让问题在写之前暴露。

> 三条自检用例（错类型 / 正确 / 幽灵字段）已在实跑中验证：**拦、放、拦**。

**④ 失败必须打到原因，不许只回数字**

`core.add_records` 只回 `(ok, fail)`。失败时用 `_write_errors()` 复跑一批取 `results[].error` 原文打印。
否则下一个人要从零复现 payload 才能知道为什么失败。

**⑤ 三态不变量**：任何分支（含"全部已在库中"）都要打齐 Triage 三态，
否则读者分不清**跳过**和**忘做**。

## 4.8 ★ 字段语义：`jar依赖` 记有无，`jar文件名` 记名字

上一版把同一个 jar 文件名同时写进两个字段，**241 行完全重复**。当时以为是"两个维度各存一份"，
实际两个字段都只有文件名，等于其中一个白存。

| 字段 | 存什么 | 回答的问题 |
|---|---|---|
| `jar依赖` | `是` / `否` | 这条线路**要不要**带 jar |
| `jar文件名` | `mojiGuard.jar` / `amns.jar` | 带**哪个** |
| `jar地址` | 下载地址 | 从哪下（**全生态无此数据源，0/620**）|

分开才有用：出包时先用 `jar依赖` 筛选（一次 select 级判断），再用 `jar文件名` 去凑文件。
两个字段都存文件名时，第一层筛选取不到值。

**实测分布（620 行，零矛盾）**

| `jar依赖` | `jar文件名` | 条数 | 含义 |
|---|---|---|---|
| 否 | 空 | 112 | 直链系，不需 jar |
| 是 | 有 | 241 | 依赖 jar 且知道是哪个（`*Guard`/`*Amns`）|
| 是 | 空 | 267 | 依赖 jar 但**未知是哪个**（待验）|

`jar依赖=是` 的 508 条 = `jar系` 总数，两个方向交叉核对均 **0 矛盾**。

**⚠️ 认不出 jar 家族 ≠ 不需要 jar。** `jar_file()` 只认 `*Guard`/`*Amns` 两类（社区公认包名），
其余 267 种自定义类名（`App99`/`PanUC`/`DuboKu`）它返回空串，但 `测活证据` 明确写着
「csp类线：依赖 jar，仅可随底包端测」—— 它们依赖 jar，只是不知道是哪个。
所以 `jar依赖` 记"是"、`jar文件名` 留空（**空 = 待验，不是"无"**）。

## 4.9 ★ 体系判定：`jar系` 指"依赖外部业务 jar"，不是"要跑起来"

`classify()` 曾把本地 `./py/*.py` 与 `./lib/*.js` 判 jar系，理由是"要有引擎 jar 才跑"。
**这条推理把「引擎」误当成了「外部业务 jar 依赖」**：

- `jar系` = 出包必须带上某个外部业务 jar，不带就起不来
- 本地 py/js = 靠 **py 引擎**（drpy2 / TVB-py）执行，与 jar 依赖无关 → **直链系**

反向验证站得住：`jar_file()` 认得出 jar 家族的 241 条，**恰好等于**库里有 jar 的 241 条，一条不差。

> **`csp_` 一律保持 jar系**，包括 `csp_PanUC` / `csp_Config` 这类看着像标准类的 ——
> 它们用的是 CatVod **标准 jar**，而标准 jar 也是 jar，出包照样得带。

S111 修正后：`直链系 112 / jar系 508`，全表 620 行与 `classify()` **零偏差**。
回填工具 `scripts/backfill_system.py`（默认预演，`--apply` 才写）。

## 5. 去重铁律

- **唯一键 = `api接口`**（完整 api 字符串），不是名称、不是 host
  - 名称不同但 api 相同 = 同一条源（例：🍋柠檬秒播 == 公众号盒子迷MAX，同 `csp_Nmvod` 同 ext）
- 去重分三层，缺一不可：
  1. **与库内已有去重**（先导出 CSV 建 exist 集）
  2. **包间去重**（多个包含同一条源）
  3. **包内去重**
- `lives` 的 url 若是多行播放列表 → 取**首行**作为该数据源的标识
- 相对路径开头的一律丢弃，**不要**试图转绝对（作者资源包已离线，转了也没内容）
- **伪源黑名单**：`blacklist.txt`（技能根目录下）。已**实测**确认为失效/伪装的源登记在此，扫描时自动剔除，避免反复入库
  - 格式：`<完整api>\t<判定原因>`，`#` 开头为注释
  - 典型伪源伪装术（判死的经验）：HTTP 200 但内容是 `<title>welcome</title>` 域名挂靠页 / `"key":"xxx"` 占位模板 / 返回 `404 Not Found` 正文
  - **铁律：HTTP 200 ≠ 可用**。新源入库前若可 curl，务必看**内容形态**而非状态码

## 6.5 ★ 四方联动引擎（规则 45 + 46）

> **源数据库 ↔ 底包库 ↔ 会话台账 ↔ 资料库经验库** 生态联动，自动触发、互相学习、流程标准化 —— 为了**加快推进、减少中间环节、节约时间**。

**四极坐标**：

| 极 | 载体 | ID | 记什么 |
|---|---|---|---|
| ① 源数据库 | 线路源库 + 成品源库（见 §1） | `pNwZ9uBOTz6FzRuvu8nryI` / `8JBrhSwsJ3pnPYtoGLo9XV` | 线路 + 可用体系 |
| ② 底包库 | 📁 底包·底包总库 | `GCLJWbFGS1BmYbj6JCX9it` | 整包 + 体系分类 |
| ③ 会话台账 | 🔗 会话台账 | `TO4LwsjVVdR8JRAUlkejk3` | **业务**经验（某接口怎么处理） |
| ④ 资料库经验库 | 📚 资料库操作经验库 | `XTuuj8mKtqnZSolDdeDxkq` | **平台**经验（资料库怎么用才不踩坑） |

> **③④ 分工**：业务经验按**任务类型**复用，平台经验按**操作类型**复用。
> 平台坑（上传 403 / 表格配额 / PropertyValue / 伪成功 / 分页 / 换行合并）是**跨业务通用**的，
> 不属于任何单个包，却每次操作都可能撞上 —— 所以单独立第四极。

**命令 → 见 §8.2 统一入口**（`tvbox brief/status/learn/lib-learn/log/lib-log/sync`，**不在此重复列表**·M-R38）。
> 速记四条：①开工第一条 `brief` ②碰业务前 `learn` ③碰资料库前 `lib-learn` ④收工双写 `log`+（有平台坑则）`lib-log`。

**自动触发铁律**（命中即执行，不问用户）：
- 新会话开工 → 先跑 `brief`
- **操作资料库前**（上传/建表/改字段/写记录/编辑文档）→ 先 `lib-learn` 查同类平台坑
- 整包入库完成 → 立刻 `sync`（L1 自动提源）
- 遇到**业务**报错/返工 → **当场** `log` 记踩坑+解法
- 遇到**平台**坑（资料库操作类）→ **当场** `lib-log`，因为下次还会撞
- 每单收工 → `log` 沉淀业务经验

**互相学习的落点**：`可复用点` 字段是**跨会话复利**的载体 —— 写清楚一条，下次同类任务直接套用，不用重新踩。

**⑥ 生态性铁律**：资料库不是仓库，是**会成长的生态**。任何一次踩坑，只要没写进 ③ 或 ④，就等于白踩 —— 下次还会再撞。写进去一次，全局永久受益。

## 6.6 ★ 数据一致性同步 + 主动触达（规则 47）

> **目的**：底包库/源库更新后，资料库侧文档必须同步；日后实现**数据一致性与精准性同步**，
> 让变动**及时更新**，并成为**主动触达**的能力，而不是等人想起。

### 唯一权威快照（根治多处记载打架）
问题根因：同一份数字散落在协作约定 / RULES / 索引 / 清单多处，一处更新其他处就过时。
实测曾出现协作约定记「192 条 / 104 条 / 6 列」而真值已是「963 条 / 537 条 / 8 列」。

**解法**：建立唯一权威快照页 📊 状态·四极现状快照（唯一权威），位于类目 `GHqCfbGoCOAOV4g4NVxsCE` 下。
铁律：**其余所有文档一律不再记绝对数字**，只引用该页；数字由 `snapshot` 自动刷新。

> ⚠️ **文档中不要写死快照 id** —— 刷新会重建页面导致 id 变化。
> 应写「取标题为…的最新一份（旧份被自动改名为 ❌已废弃_快照_日期）」。
> 当前有效 id 由本技能维护在 `snapshot_id.txt`。

### 同步引擎（两条命令）

| 命令 | 用途 |
|---|---|
| `link.py audit` | **一致性对账**：拉四极真值，扫描文档记载，列出「文档值 → 真值」不一致 + 处置建议 |
| `link.py snapshot` | **刷新权威快照**：重采真值并重建快照页；`--dry` 只预览不写云端 |
| `link.py sizes` | **只读四极规模**（单行）：`源库 N \| 备用 N \| 台账 N \| 经验库 N`。供评估/只读场景用，**绝不写云端**——区别于 snapshot 的写副作用 |

刷新机制：整页重建（脚本生成页，重建最稳）→ 旧页自动 rename 为「❌已废弃_快照_MMDD_HHMM」（符合规则 35，API 无删除能力）。

### 主动触达铁律（命中即执行，不等用户开口）
1. 任一极**数量变动**（入库 / 新增包 / 新增台账或经验条目）后 → **立即** `snapshot`
2. 任一极**结构变动**（加列 / 加体系 / 新建文件夹）后 → 立即 `snapshot` + 在协作约定/RULES 补指针
3. 新会话开工跑 `brief` 后，若本会话有数据变动 → 收工前自动 `snapshot` 一次
4. 用户问「现在有多少条 / 库里什么状态」→ **以快照页为准回答**，不凭记忆、不凭旧文档

### 精准性要求
- 数字必须**实测拉取**（`get_database_content` / `list-nodes`），禁止估算或沿用
- 对账要定位到「文档名 + 字段名 + 旧值 → 新值」粒度，不能只说"有出入"
  - 历史数值属正常留痕，标注「以快照页为准」即可，不必删除

# 自检规范 · 四要素（self_probe_spec）

> **来源：探源司 33 条自检的提炼。实测 33/33 全是四元组，无一例外。**
> 本文是"技能落地"的唯一验证标准。任何技能声称"我有自检"，必须能对号入座本文。

---

## 一、为什么需要这份规范

探源司 `tvbox probe self-check` 输出 33/33，用户满意。它不是靠"多写检查器"，而是靠**每条检查都被证明可证伪**。

反观其他 63 个技能：**没有任何一条自检**。所以它们"能用"只是口头声称。

本规范把探源司的做法固定下来，让其他技能可以照着做。

---

## 二、四要素（缺一不可）

每一条自检必须包含四样东西：

### ① 被测目标（Target）

**指向生产代码里的哪个函数/判定。**

```python
# ✔ 正确：直接调真实函数
hit_alive = _alive_verdict(404) == '已封禁/删除'

# ✘ 错误：另写一份模拟逻辑
def mock_verdict(x):  # 测试里重写了一遍判定
    return '已封禁/删除' if x == 404 else '存活'
hit_alive = mock_verdict(404) == '已封禁/删除'
```

**为什么**：测试重写一遍逻辑，等于测的是测试自己。生产代码坏了它照样绿。

### ② 坏样本（hit）—— 必须捕获

喂一个**必然违规**的输入，检测器必须报出来。

```python
hit_alive = _alive_verdict(404) == '已封禁/删除'
```

### ③ 好样本（clean）—— 必须清零

去掉坏样本后，检测器必须归零（不许残留、不许误报）。

```python
clean_alive = _alive_verdict(200) == '存活'
```

### ④ 边界样本（base）—— 必须"无法判定"

喂一个**测不出来**的输入，检测器必须明确说"我不知道"，**不许报通过，也不许报失败**。

```python
base_alive = _alive_verdict(0) == '无法判定'   # 0 = 网络不可达，不是"站死了"
```

## 三、三缺一就是三种病

| 缺失 | 病症 | 后果 |
|---|---|---|
| 只 hit，不 clean | **哑巴**（恒报红） | 检测器永远报警，人就不看了 |
| 只 clean，不 hit | **聋子**（真坏了不响） | 看起来正常，实际全瞎 |
| 缺 base | **瞎**（把"测不出来"当"没问题"） | 网络断了、文件没了、权限不够，统统报绿 |

**第三种最毒**，因为它伪装成"一切正常"。今晚我犯的 `except: X = None` 全是这一类。

---

## 四、三类的验收标准（按技能性质分，不许混）

| 类 | 特征 | 自检标准 | 标记 |
|---|---|---|---|
| **A 判定型** | 内部有判定/校验/过滤/去重/归一函数 | **完整四要素** | `verified` |
| **B 命令型** | 能跑命令出结果，无判定逻辑 | **冒烟三件套**（见下） | `smoke` |
| **C 工具型** | 纯操作手册 | **只验可调用**（见下） | `callable` |

### B 类冒烟三件套

```
① 能跑通     —— rc = 0
② 输出有内容 —— 关键字段存在（不是空表）
③ 空输入不崩 —— 传空参数不 crash，且必须"报错或返回空"，不许静默成功
```

**第③条是 M-R80 的落地**：数据源缺失时，必须报"无法判定"，不许报"0 项"。

### C 类只验三条

```
① SKILL.md 存在且 frontmatter 有效
② description 里有触发词（只认 frontmatter，不抓正文 —— M-R76/M-R27）
③ 能用一句话路由到它
```

**C 类严禁标 `verified`。** 给"写 PPT 的技能"写判定探针，只会造出假绿（M-R113）。

---

## 五、自检自身必须有心跳

**M-R63 / M-R32：检测器失效 ≠ 检测器无发现。**

每条自检必须能证明"我活着"：

```
喂一个必然让自检崩溃的输入（如不存在的文件路径）
→ 自检必须报错（exit 2 或明确异常）
→ 如果不报错而是静默通过，说明自检本身失效
```

---

## 六、写自检时的检查清单

开工前后各过一遍：

- [ ] 被测目标是真实函数，不是模拟
- [ ] 坏样本真的坏（不是把好样本改个名字）
- [ ] 好样本真的能清零（不是"我以为清了"）
- [ ] 边界样本真的无法判定（不是把失败包装成无法判定）
- [ ] 自检自身失败会报错（心跳）
- [ ] 自检命令能独立跑，不依赖总闸门（M-R118）
- [ ] 登记前当场跑过一次，rc=0（M-R105）

---

## 七、反例：今晚真实踩过的四个

| 反例 | 违了什么 | 正确写法 |
|---|---|---|
| `except: _CORE = None` | 缺 base，读失败折叠成"没有" | 返回 `(模块, 失败原因)` |
| 注入测试后 `delta=0`，以为判据失效 | 观测本身错了，不是判据错 | 观测必须有 base（先确认为什么 0） |
| `reload` 后测，测的是旧模块 | 被测目标不是真实函数 | 用子进程，确保加载新代码 |
| 同一个凭证号测两次，第二次被幂等跳过 | 好样本被污染 | 每次注入用唯一凭证号 |

## 八、给探源司加 `--json` 时踩到的三个坑（S177 步2，全部实测）

这三个坑的共同点：**不报错、不告警、命令"看起来跑了"**。是"静默失效"的教科书样本，必须写死进规范。

### 坑 1：参数名撞模块名 → 开关恒真但不生效

```python
import json                                   # 顶层
p.add_argument('--json', action='store_true') # 目的地默认就叫 json
if getattr(a, 'json', False): ...             # 拿到的是 json 模块对象，恒真
```

**症状**：开关"总是开着"，代码块"总是执行"，但真跑起来一行输出都没有。
**根因**：`getattr(a,'json')` 在 Namespace 上没有该属性时，`getattr` 的默认值是我写的 `False`，
但 argparse 确实设置了 `a.json`……问题在于**后续代码里 `json` 这个名字被模块占用**，
于是 `json.dumps` 与"参数值"是同一个名字，读到的东西取决于绑定顺序。
**治法**：目的地必须换名——`add_argument('--json', dest='as_json')`。

> 判据：**参数名与任何已导入模块名不得重名**。检查成本是一行 grep，代价是一整晚的排查。

### 坑 2：长函数里参数被局部变量覆盖 → `getattr` 永远拿不到

```python
def cmd_self_check(a):          # a 是 Namespace
    ...
    a = _score_repo(4240, ...)  # ← 1300 行之后，a 变成了 '59.8'
    ...
    if getattr(a, 'as_json'):   # 永远 False，因为 a 现在是字符串
```

**症状**：与坑 1 完全一样——不报错、无输出。
**实测证据**：用 `sys.settrace` 在 `if` 那一行读 `frame.f_locals['a']`，值是 `'59.8'`。
**根因**：函数超过几百行后，参数名被当成随手可用的局部变量名。
**治法（从根上，不是改局部变量）**：**参数一进门就锁进专用名字**。

```python
def cmd_self_check(a):
    _opt = a        # ← 这一行是整个函数的安全带
    # 后面谁再覆盖 a 都伤不到 _opt
```

> 判据：**任何超过 100 行的函数，参数必须在第一行复制到 `_opt` 这类专用名**。
> 不要指望"我会记得不覆盖它"——1300 行里没人记得。

### 坑 3：`sys.exit(1)` 写在证据输出之前 → 越该报红越没证据

```python
if ok != len(results):
    sys.exit(1)          # ← 先退
if opt.as_json:
    print(json.dumps(...))   # ← 永远走不到
```

**症状**：33/33 全绿时有 JSON；某条探针坏掉时 **exit(1) 直接退，一行 JSON 都没有**。
外部程序只拿到退出码，**判红的证据全部丢失**。
**这个坑只有真注入坏样本才会暴露**——我第一版写完，跑全绿样本一切正常，
直到把 `_alive_verdict` 打坏，才发现"越需要证据的时候越没有证据"。
**治法**：**先把证据吐出来，再 exit(1)**。顺序不许调。

> 判据：**任何 `exit(非0)` 之前，必须已经输出了判定依据**。
> 与 M-R63 同型：报红是真的，但报红的原因丢了，等于只告诉人"有事"，不告诉人"什么事"。

### 坑 4（已修，S177 步2.5）：探针自身抛异常会整段崩掉

```python
hit_alive = _alive_verdict(404) == '已封禁/删除'   # 若 _alive_verdict 抛异常
```

**症状**：Python traceback 直接冒到屏幕，33 条红绿清单**一条都不打印**，JSON 也没有。
**这意味着**：**只要有一条探针的被测函数抛异常（而不是返回错值），
整个自检就变成"无声崩溃"**——人看到的是一屏 traceback，
既不知道其余 32 条是绿是红，也不知道这条到底测出了什么。

**与 M-R63 的关系**：M-R63 是"检测器坏了还报绿"（骗人），
这个是"检测器坏了连绿都不报"（让人无从下手）。两者都要防。

**修法：唯一正解是这个形态，不许自创**

```python
hit_x = clean_x = base_x = False       # ① 先落 False：默认"判定不成立"
try:
    hit_x = ...真调用生产函数...        # ② 断言内容一个字不改
    clean_x = ...
    base_x = ...
except Exception as e:
    print(f'  ⚠️ {探针名}探针异常：{type(e).__name__}: {e}')   # ③ 原因必须露出来
results.append((探针名, hit_x, clean_x, base_x))               # ④ 无论如何都记一条
```

四条缺一不可：

| 缺 | 后果 |
|---|---|
| 缺 ① | 异常时变量未定义 → 后面 append 再崩一次 |
| 缺 ② 改成"自己写一遍判据" | 变成 mock，违反四要素第一条 |
| 缺 ③ | 静默吞异常，违反 M-R60；人只知道红不知道为什么红 |
| 缺 ④ 把 append 挪进 try | 异常时这条**整个消失**，33 条变 32 条，人看不出少了一条 |

> **④ 最容易写错**：直觉会想"出错了就别记录了"，但这恰恰最危险——
> 条数从 33 变 32，没有任何提示。**少一条比红一条更难看懂。**

**实测（S177 步2.5，9 个生产函数逐个打坏）**

| 打坏的函数 | rc | 红绿条数 | JSON | 判坏条目 |
|---|---|---|---|---|
| `_alive_verdict` | 1 | 33 | 有 | 存活判定器 |
| `_content_sha` | 1 | 33 | 有 | 内容指纹 |
| `_dir_diff` | 1 | 33 | 有 | 目录差集 |
| `_activity_verdict` | 1 | 33 | 有 | 活跃度判定 |
| `_parse_ts` | 1 | 33 | 有 | 多平台适配, 活跃度预测 |
| `_parse_repo` | 1 | 33 | 有 | 多平台适配 |
| `_forecast_risk` | 1 | 33 | 有 | 活跃度预测 |
| `_cand_id` | 1 | 33 | 有 | 上云upsert与指纹幂等 |
| `_harvest_id` | 1 | 33 | 有 | 上云upsert与指纹幂等 |

修完 33/33 与修前完全一致——**判定逻辑零改动**，只加了外层保护。

### 坑 5（摸底时的认知修正，值得记）：不是"33 个洞"，是"两种写法"

修复前我的判断是「33 条探针全是裸调用」。用 AST 逐条查才看清：
**前 7 条没跟上后来的写法，后 26 条早就有 try**。

这是同一个文件里历史演进留下的不一致，不是设计失败。
**教训**：动手前先量，别按印象估工作量——按"33 处"估会想找统一方案，
按"7 处"就知道直接补齐最快。**量一次的成本远低于照错估去做**。

### 本次四个坑的共性判据（可复用到任何技能）

| 检查 | 手法 | 成本 |
|---|---|---|
| 开关真的有效吗 | **同时跑带/不带两种**，比对输出差异（不是看代码） | 2 条命令 |
| 参数真的传到了吗 | `sys.settrace` 在判断行读 `f_locals` | 10 行脚本 |
| 报红时证据还在吗 | **真注入坏样本**，检查证据与退出码同时存在 | 1 次注入 |
| 探针崩了会怎样 | **逐个打坏被测函数**，看条数是否齐、是否点名 | 每个函数 1 次 |

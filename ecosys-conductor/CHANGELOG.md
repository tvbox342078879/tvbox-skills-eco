## v1.75.0 — version_guard 把「未登记」当「一致」+ 分层判定 EI 作用域崩溃（S176）

### 缺陷一：`version_guard` 的 `status` 停在初值就当成对

`collect()` 里：

```python
elif v_eco and v_skill and v_eco != v_skill:
    status = 'drift'
```

`v_eco` 为 `None`（云端生态库**压根没这一行**）时，整条 `elif` 短路，`status` 停在
`'ok'`。于是 `automation-task-manager`（生态库未登记）在表里显示成 `-`，却算 ✅，
结论行还打「✅ 全部一致（13 个自建技能）」——**先列完 1 个未登记，紧跟着说全部一致**。

这是 M-R60「读不到/没有 ≠ 对」的**第三次同形复发**（前两次：快照读失败折叠成无历史、
hub 读表失败折叠成空库）。

**修法**：单列 `unregistered` 状态，计入分母、计为不过，且未登记时不打印「全部一致」。
实测修后：`⚠️ 12/13 个自建技能三处一致，1 个生态库未登记`（exit=1）。

### 缺陷二：`EI` 作用域错误——「降级」从来没生效过，一直是崩溃

`conductor.py` 分层判定里：

```python
try:
    import eco_inventory as EI     # ← 在 try 内
    ...
except Exception:
    layer = None
if layer == EI.PLATFORM:           # ← 在 try 外，import 失败时 EI 不存在
```

import 一失败，`EI` 这个名字根本没被创建，两行 `if` 立刻抛
`UnboundLocalError: cannot access local variable 'EI'`。外围还有一层
`except: 该技能脚本缺失（降级跳过）`，于是崩溃被包装成"降级"——**双重折叠**。

实证：`signal-check` 报

```
❌ 探针静默异常：1 个检测器抛未捕获异常
   信号源5 路由盲区：UnboundLocalError: cannot access local variable 'EI'
```

**修法**：`EI` 的导入提到 `try` 外，导入/调用各自兜住并显式置 `None`；
两个分层分支加 `EI is not None` 前置。修后 signal-check `45/45`，静默异常消失。

> **自省**：这段代码是我先登记进折叠扫描白名单、并在注释里写「后续 if 会走老逻辑」的。
> 那句话是错的——白名单让我以为它是对的，于是没去看。**白名单只该登记"已证明安全"的
> 折叠，不该用来放行"我读着觉得安全"的代码。**

### 同时：`finalcheck ③` 的分母会悄悄少 1

账房 `finalcheck ③` 解析 `version_guard` 明细的正则要求四列全是数字，而未登记行的
生态库列是 `-`，整行不匹配 → 被跳过 → 分母跟着少 1 → 永远显示"全部一致"。
已在账房侧放宽为允许 `-`，并把 `-` 的行单列「生态库未登记」计为不过，
同时校验「守卫报的技能数 == 实际解析行数」。

### 验收

```

conductor verify          → 7/12 → 8/12（① 探针 45/45 基线净，静默异常消除）
```

## v1.72.0 — `drift-fix` 闭环 + 缓存两层坑：同一个坑第三次踩，这次把它焊死（S162）

### 起因：用户一句「怎么你还在手搓」

上一轮做完了 `--sync-eco`，看着像是"台账回写通了"。可这一轮升 probe-hub 版本时，
我依旧在手工做三件事：先跑 `version_guard.py` 看漂没漂、再跑 `--sync-eco` 回写、再跑一遍确认。

M-R71 的原话是「用工具代替记忆」。**工具在、但顺序还记在人脑里，就等于没工具。**
忘任何一步，台账就停在半路，而且没有任何东西会报警——这正是上一轮 6 处漂移能活下来的原因。

### 这轮踩的坑（三个，全是"看起来对"）

**① 缓存有两层，我只堵了一层（同一个坑第三次）**

升 1.10.0 后跑 `--sync-eco`，报「回读仍为 1.9.0——未落库」，rc=1。云端其实早写进去了。

我先判断成「接口读缓存有几十秒延迟」，于是加了退避重试（1s/2s/3s）。**判错了**：
3 次全读到旧值，跑了 4 秒还是失败；开新进程一测，**0 秒就读到新值**——矛盾。

真根因：`core` 有**两层**缓存
- ① `rows_of_t` 的 db 键
- ② `api()` 的 `('api',script,args)` 键

上一轮的修法 `rows_of(DB_ECO, _cache=False)` **只跳过 ①**，仍调 `api()`，而 `api` 默认 `_cache=True`
→ 同进程内第二次读照样命中旧值。

而 `core.invalidate` 的注释里就写着：「坑（S020 实测复发，同症状第二次）」。
**同一个坑，第三次踩。** 补一行 `invalidate(DB_ECO)` 后，1.8 秒一次通过（1.9.0 → 1.10.0）。

**② 解析输出时不校验"解析到空"，把有漂移报成"无需回写"**

`drift-fix` 第一版按 `'漂移' in line` 抓行，抓到的是标题行「🔴 发现 1 处漂移：」
——冒号右边是空的、没有 `SKILL=`，于是 `need_eco` 为空 →
**明明有漂移，却打出「✅ 无需回写」并 rc=0**。假绿比漏修更坏。

**③ 键名带前导空格，把正常漂移误判成"本地写错"**

行格式用 ` / ` 分隔，`dict(p.split('='))` 得到的键是 `' CHANGELOG'`（带空格），取不到值。
于是正常的云端滞后被报成「本地两列自相矛盾」。

②③ 病根同一条：**解析别人打印的文本，却不校验解析结果是否为空/合理。**
空结果被当成"没问题"——这是所有 parse-then-act 工具的通病。

  - 铁律1：**复检说了算**。`--sync-eco` 的 rc 只用于判断"要不要继续"，不用来下结论

| ② 写错字段 | 回读某个字段变了，但不是那个 | 回读**指定字段** |
| ③ **写错行** | 回读确实变了——变到别人身上了 | 写入前**反向核对 id→name** |

回读挡不住第③种：它只问「这个值对不对」，不问「这个值落在谁身上」。

**③ `recs` 里没带 `skill`，核对段一引用就 KeyError。** 它一直没崩，因为前面几次跑
全都「无需回写」——**空分支掩盖了崩溃点**。教训：全绿路径没跑过的代码不算写完，
写判据必须用能进分支的合成输入试。

**④ 回读把 `None` 判成「未落库」，而下一行结论写「全部对齐」。** 同一函数两句自相矛盾。
根因：`collect()` 只收有 CHANGELOG 的技能，插件市场技能（library）不在表里，
`after.get()` 得 None。三态没分清：**读不到 ≠ 写失败 ≠ 一致**。

### 四、拆防线反证（别只验「能通过」）

| 拆掉什么 | 结果 |
|---|---|
| 只拆「写入前核对」 | `rc=1`——**回读**也拦住了（目标行没变） |
| 同时拆「核对 + 回读」 | `rc=0`，`9.9.9` **真被写进 library**（已还原，无残留） |

结论：这两道**不是冗余，是互补**——
核对挡「将要写错」，在发请求前，一个字节都不发出去；
回读挡「已经写错」，事后发现，但**只能发现、不能阻止**（数据已脏）。

### 一、体检发现的真问题：M-R60 只落在了 `core.rows_of_t` 一家身上

### 二、修掉 4 处「静默假绿」（这是本轮最实的收获）

不是"改写法"级别的整理，是**真会骗人的 bug**：

1. **`blk.py:_update_dead`** —— 只看 `returncode==0` 判成功。而 library 的批处理脚本
   在「接口通了但记录没更新成功」时**仍返回 0**（失败信息在 `results[i].success` 里）。
   实测意味着"更新失败会被当成成功"。
2. **`link.py:_paged_records`** —— `except: break` 直接跳出，返回**已读到的那几页**，
   调用方拿它当全表 → 按它算出的增删会漏掉后面几页。
3. **`probe_src.py:_paged`** —— 同上，且回写时把"读失败"与"该库无记录"混为一句。
4. **`link.py:cmd_audit`（非本轮引入，但被本轮查出）** —— 整个后半段 63 行

   的 `return` 之后，成了**死代码**，从未执行过。修好后实跑输出 8 处数值差异（均已是历史留痕）。

### 三、`core.py` 新增资料库读写统一协议（`_run_lib` 是唯一调用姿势）

- `_run_lib(script, *args)` → `(ok, stdout, err)`，脚本缺失/子进程异常/非零退出**全部三态**
- `_parse_results` → **绝不在解析失败时返回"全成功"**
- `update_records` → `(ok, n, info)`，含 **properties 结构误用检测**：
  写成 `{"字段名": 值}` 会直接提示 `须写成 {"字段名": {"text": "值"}}`（S158 实测踩过的坑）
- `delete_records` → **不接受"条件删"**（S144 清空三库就是条件误判）
- `write_and_verify` → 写前建基线 → 写 → 读回比对

  再拼一套 subprocess + json（**那正是协议被绕开的起点**）

### 四、两条常驻检测器（用户验收标准）

**信号源40 · 资料库调用协议**：扫全生态 `subprocess.run(...LIB...)` 调数据库脚本的位置。
两档判定：硬（无三态，strict 下必报零）/ 软（有三态但绕过 core，仅提示）。

**信号源41 · 静态未定义名**：用 pyflakes 扫全技能。
立它的原因很具体——本轮改 5 处调用姿势，**3 处留下了改前的旧变量**（`out` / `out_json`），
代码**语法完全合法、`py_compile` 通过**，只在失败分支才爆，且都被 `except` 吞成别的问题。
信号源39 只做 `py_compile`，守的是"语法坏"，守不住"名字坏"。

顺带查出两处长期哑巴：
- `conductor.py` 自己写 `time.strftime` 却**从未 `import time`** → 一直抛 NameError 被

- `probe.py` 打印剔失清单路径用了不存在的 `out_json`（真名 `rep`），被外层 except
  吞成「生态门面联动跳过」，人以为只是门面没连上。

### 五、三条"检测器抓自己"的教训（都是本轮自己踩的）

1. **探针被自己扫到**：`_sig_lib_protocol` 扫到了注入的 `_probe_lib_raw.py`，
   健康态恒报一条硬违规 → 进假阳性基线 → 逼人去调基线数字（等于把检测器关掉）。
   修法：扫描器跳过 `_probe_` 前缀，同时给探针验证加 `include_probe=True` 专门放行，
   **"能不能抓到"仍然被真实验证**，不是因为文件名被排除而假装通过。
2. **`evolve.py` 的 `except: ok = 0`**：把「通路坏了」折叠成「成功了 0 条」，
   下游照打「api 自报成功 0 条」——等于替失败编了个看起来正常的数字。改成 `None` 哨兵 + 分流。
3. **登记了编号却漏了 `_sig_health` 自检**：正是该函数自己要防的「装健康的哑巴」。

**共性**：`None` / `0` 在语法层长得一模一样，静态扫描**分不清"三态哨兵"与"折叠成空"**。
这不是扫描器的缺陷，是它的固有边界——故只能人工审计后登记白名单，每条附理由。
但**白名单不许用来藏缺陷**：一旦用来藏，它就是第二个 `except: pass`。

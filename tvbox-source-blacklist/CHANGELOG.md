## v1.1.14 — `review --single` 默认等于不干活：73 条一条都不跑

### 起象：失效库 2 天没被复查过
`blk stats` 显示 220 条失效源、复测时间停在 **2026-10-17/18**。用户要求闭环时实跑：

```
$ blk.py review --single
单条复测 0 条（共 73 条单条类；待复测 0 条，本次跑 0 条）…
  → 无待复测项
```

**73 条单条类，100% 都是「复测结果=仍失效」**，而默认筛选只要「未复测/待复测」：

```python
# 修前
todo_all=[r for r in tg if r.get('复测结果') in ('未复测','待复测')
          or (a.recheck and r.get('复测结果')=='仍失效')]
```

于是默认跑 0 条、**正常退出、不报错**——看起来像"已经都测过了"。
原注释写「默认仍只跑待复测，避免每次全量」，本意是省流量，实际效果是**永远不复查**。

### 更糟的：两条路径行为相反
| 路径 | 是否按复测结果过滤 | 实际效果 |
|---|---|---|
| 整域 `cmd_review` | **不过滤**，每轮全跑 145 条 | 一直很勤 |
| 单条 `cmd_single_review` | 过滤，只要"待复测" | **永远不跑** |

同一命令的两半，一半每轮全量、一半永久停摆。

### 修
默认纳入「仍失效」，并按**停滞天数降序**（最久没查的排最前），使 `--limit N`
永远优先覆盖最该复查的那批：

```python
cand=[r for r in tg if r.get('复测结果') in ('未复测','待复测','仍失效')]
cand.sort(key=_stale_days, reverse=True)
```

`_stale_days` 解析 `复测时间`（两种格式都兜），缺失/不可解析 → 9999（最高优先）。
`--recheck` 保留原语义（额外纳入非三态的历史记录），老调用不失效。

### 复现与验证
```
默认 --single 会跑 0 条   →  修后 73 条（按停滞时长排序）
加 --recheck 会跑 73 条
```

### 附带发现（未改，仅记录）
判死规则本身是**对的**，不要去"优化"它：
- `judge_level()` 明确写了「单次失败永不判 L1」「证书类封顶 L2·续期可恢复」
- 50 条「暂判死」中 47 条 `连续失败次数=1` —— 这正是规则在正常工作
- 真正的问题不是"判太快"，是**判完之后没有定期回头复查**（本次修的正是这个）

误杀检测工具 `probe.py blacklist audit` 早已存在（S169 就写了，实测在 172 条 L1 里
捞出 5 条误杀，其中 2 条有 8.7 万/30 万条真实数据，误判原因是没带 UA 被 CF 拒），
但**没有任何调度在跑它** —— 工具造好了却没接进流程，等于没有。

## v1.1.12 — 触发词划界 + 真源回填（S157）

S157 做技能指向核查，发现 6 个触发词同时归两个技能（`监测/生态/对账/终验/直链/轻量json`），
同分时靠列表顺序决胜负——用户问记账被推给总指挥、要看体检被推给处置层。

本技能相关划界：

- **legacy-watchdog 去裸词 `监测`**：判据是「遗迹哨不是"盯"的人，是拿到盯的结果之后
  派人去修的人」。裸词归监察司，本技能留 `遗留监测/老问题监测/处置/派活/账龄/分级`。
- **tvbox-source-blacklist 去裸名词 `失效源`**：`失效源` 是事物不是动作。
  「有多少个失效源」是盘点（归监察司）、「这个失效源拉黑」是治理（归本技能）。
  故名词让给盘点方，本技能只留**治理动作**（拉黑/封掉/拦截/标一下）。
- **probe-hub / tvbox-interface 分 `直链`、`轻量json`**：探源司"从上游找"、
  整包坊"把手上这份加工"。裸名词从两家都移出，各留带动作的短语。
- **skill-evolution / tvbox-interface / probe-hub** 回填 M-R76 真源：
  `_SKILL_INTENTS` 里新增的词同步进 description，否则信号源32 报"投影孤儿词"
  （打分器认识、模型看不见，用户这么说模型想不起该用哪个技能）。

**这轮实测结论要记住**：补词只能拟合不能泛化——按一批口语补到 100%，
换一批从没见过的掉回 47%。故 `conductor ask` 已改为**候选+依据**输出而非单选。

## v1.1.10 — 复活回写其实一直在静默失败：常量与库 schema 从未对齐（S159）

**这条最值得记**：`REASON_*` 系列常量从 v1.1.3「失效原因枚举化」起就长这样——

```python
REASON_FULL  = '整域全灭（host 下全部源失效）'
REASON_PART  = '单源失效（同 host 下其它源仍可用）'
```

**带着括号解释句**。它们是 `select` 字段的取值，平台遇到非法值**静默丢弃**、不报错。
于是每一次「复活回写」都执行成功、都不生效，账面看着归档了，实际什么都没写。
骗了整整 6 个版本。

**枚举值实测校正**（`get_database_schema.py` 取得，非记忆）：

| 字段 | 合法值 |
|---|---|
| `拉黑范围` | 整域 / 单条 / **观望** |
| `失效原因` | 整域全灭 / 单源失效 / 假活 / 入库拦截命中 / 严格采样误判 / URL无法解析 / 人工拉黑 |
| `判死状态` | 暂判死 / 确认死 / **已平反** |
| `复测结果` | 仍失效 / **已恢复** / 未复测 |
| `拉黑层级` | L1精确黑 / L2观察 / L3域名预警 |

**改动**：
- 常量全部改为**裸枚举字面值**；
- 复活回写改三态语义：`复测结果=已恢复` + `拉黑范围=观望` + `判死状态=已平反`——
  复活不是「删掉拉黑记录」（那是销毁证据），而是「从拦截转为观望」；
- `'待复测'` → `'未复测'`（原值也不存在）；`cand` 兼容 `('已恢复','已复活')` 读旧数据；
- `cmd_mark` 加**读不全守卫**：源库读失败或为空时**中止整域拉黑**，绝不拿空集当"零命中"；
- `cmd_archive` 加三态守卫；
- `PLATFORM_HINT` 补 `cnb.cool` / `git.yylx.win`（前者是代码托管平台，后者是自建 git，
  都属 S026 定的「代理型 host 永不参与整域拉黑」家族）。

**教训（已回写经验池）**：**字段字面值 ≠ 语义**。M09 曾用 `拉黑范围 in ('整域','单条')`
判「是否在拦」，但 `观望` 同样在拦（只是层级低）——按字面值算就漏判。
现改为按 `BLOCKING_SCOPES` 语义判据。同时**枚举是外部契约，代码不许按记忆写死**（M-R99）。

**实测**：M09 僵尸源 3 项 → **0 项**。独立复算反验：129 个整域 host、12 条停用记录参与计算，
源库正常记录落在整域黑名单上 = **0**，确认非假绿。

## v1.1.9 — 整域拉黑的两类「不许整域」被写成了整域（S151）

### 起因

清账 M09 僵尸源（188 项）时，本是当「数据处置」在看的。抽查第一条：

```
https://raw.githubusercontent.com/Kimentanm/aptv/master/m3u/iptv.m3u
```

`blk check` 对它 🚫 拦截。但继续测：

```
https://raw.githubusercontent.com/Guovin/iptv-api/gd/output/result.m3u   🚫 拦截
https://raw.githubusercontent.com/any/other.m3u                          🚫 拦截
```

**整个 GitHub raw 被拦死了。** 原因：2 条 m3u 失效 → 被写成「整域」。

### 这是代理型缺陷的同族第二例

S026 早就定过这条规则——代理型 host 永不参与整域拉黑，因为：

> 代理域名的可达性由**被代理的目标**决定，与代理域名本身无关。

公共平台域是同一个道理的另一面：

> 平台域名下挂的是**无数互不相关的发布者**，失效的是某个发布者的某条路径，不是这个平台。

两类都不是「这个域死了」，都不该整域。S026 只堵了代理型，平台型从没堵过。

### 修了什么

**① 写侧新增平台域保护**（`is_platform_host` + `PLATFORM_HINT`）

`mark` 时平台域与代理域一起剔出整域名单，只走单条：

```
⚠️ 平台型 host 跳过整域拉黑 1 个：raw.githubusercontent.com
   （原因：平台域下是无数互不相关的发布者，整域拉黑会把整个平台判死）
```

**② 读侧同步过滤**（`blocked_set`）

写侧修的是未来，**读侧修的是现在**——存量脏数据还在表里，不滤就等于没修：

```python
hosts={h for h in hosts if not is_platform_host(h) and not is_proxy_host(h)}
```

代理域这块 S026 只改了写侧，**读侧一直没滤**，于是 `gh-proxy.com` / `ghfast.top` /
`fastgit.cc` / `gh-proxy.org` 共 12 条整域残留照旧全拦。

**③ 存量数据降级（不删）**

| 类别 | 条数 | 处置 |
|---|---|---|
| 平台域写成整域 | 2（`raw.githubusercontent.com`） | 降级为「单条」 |
| 代理域写成整域 | 12（4 个域） | 降级为「单条」 |

**只降范围、不删记录**——失效事实是真的（这两条 m3u 确实死了），只是不该由它
判死整个域。降级后备注写明原因，可追溯。

### 反向验证

| 输入 | 期望 | 实测 |
|---|---|---|
| `raw.githubusercontent.com/Guovin/...`（活跃仓库） | 放行 | ✅ 放行 |
| `raw.githubusercontent.com/Kimentanm/...`（真失效那条） | 拦截 | 🚫 单条拦截 |
| `gh-proxy.com/https://...` | 放行 | ✅ 放行 |
| `ghfast.top/https://...` | 放行 | ✅ 放行 |
| `ryzy.tv` / `ikunzyapi.com` / `api.ukuapi.com` | 拦截 | 🚫 整域拦截 |
| `www.baidu.com` | 放行 | ✅ 放行 |

**精确性与覆盖面同时成立**：真死的照拦，同域无关的放行。

### 连带修了检查器（`tvbox-inspect` M09）

M09 报 188 项僵尸源，其中 27 项是**检查器自己造的假红**：它按「表里有 host 就算命中」
判，而拦截器早已在读侧放行这两类域——**执行器放行、检查器报"你没停用"**。

判据必须与执行器同口径，否则检查器会持续制造噪声，把真实欠账淹掉。
现在 M09 的 `dead_hosts` 也套同一套过滤，剩 **158 项真实欠账**（源库标「待查」
但确实已命中单条拉黑）。这 158 项属数据处置，待用户决定。

### 一句教训

> **"整域拉黑"是一把很钝的刀。它只对「独占域名的私人站」成立。**
> 代理域和平台域都不满足这个前提，而规则里只写了代理域一种。
> 规则写「例外」时，要写的是**判据**，不是枚举——枚举永远漏下一个。

## v1.1.8 — 搬库只搬了一半：黑名单静默失效（S150）

### 用户追问起点

> 「有一次你问我要不要复测，我叫你删了，看看是不是这个问题」

查证结论：**不是删除造成的，数据一条没丢**。是**搬库搬了一半**。

### 事实链（每一环都有实证）

1. **新库存在且有数据**：`hGwE41OpJDOR8CW0sLUwRx`「探源司·失信host库」**225 条**
   （172 整域 + 53 单条），旧库 `92dSuG6uUbxitGuyx4Saaf` 为 0 条。
2. **只有 2 个地方切到了新库**：`probe-hub/probe.py`、`ecosys-conductor/conductor.py`。
3. **另外 3 个仍在读旧空库**：`blk.py` / `link.py` / `inspect_engine.py`。
4. **后果**：`blk check` 查空库 → 一律放行。实测三个已知坏源
   （`ryzy.tv` / `ikunzyapi.com` / `api.ukuapi.com`）**全部返回「✅ 放行」**。

> **黑名单当时是完全失效的，而且没有任何报错。** 这是最坏的一种：拦截器写着"在跑"，
> 实际什么都不拦，坏源照常入库。

### 根因不止一处：枚举值也换了

切到新库后仍然全部放行，因为新库把 `拉黑范围` 枚举值简化了：

| | 旧库 | 新库 |
|---|---|---|
| 整域 | `整域(host全灭)` | **`整域`** |
| 单条 | `单条(部分失效)` / `单条(host为空)` | **`单条`** |

而代码写的是 `r.get('拉黑范围') == '整域(host全灭)'` **精确相等** → 集合恒为空。

**写入侧更危险**：`blk.py` 三处写入仍写旧枚举值。`select` 写非法值平台**静默丢弃**
（M-R99），回执照样 `success: true`——于是新拉黑的条目会「写成功但拉黑范围是空的」，
下次既不算整域也不算单条，等于**新记录的拦截能力一开始就是残缺的**。

### 修法

| 文件 | 改动 |
|---|---|
| `blk.py` | 库 ID → 新库；读写两侧共 **8 处**枚举：读改**前缀匹配**（`startswith('整域')`），写改用新枚举值 |
| `link.py` | 库 ID → 新库；写入枚举改 `单条` |
| `inspect_engine.py` | 库 ID → 新库；整域判定改前缀匹配 |

读侧一律用前缀匹配而非精确等：**枚举是外部契约，代码不许按记忆写死**（M-R99 同族）。

### 反向验证

## v1.1.7 — 触发词改造：从「写了触发词」到「真能被触发」（S148·M-R104/M-R76）

**病根（S148 实测证据）**：一次长会话 12884 次工具调用里 `Skill` 只被调用 **3 次**，
生态 10 个技能**全部 0 次触发**，全程直接 `python3 scripts/xxx.py`。用户原话：
「我发现对话中并没有技能被触发，我还是纯手工的样子」。

**三层根因**：
1. **description 被 YAML 截断**——`description: "…"` 里写裸换行，解析器在第一个换行处
   截断，后半段（含全部触发词）在系统层面根本不存在。实测 874 字只剩 454 字。
2. **触发词只有术语、没有用户会说的话**——用户说「哪个底包能加更多线路」，
   而技能只认「探源/采集线路」，路由打分 0。
3. **黄金用例自测自绿**——`ROUTE_GOLDEN` 只有维护者自己编的术语，用自己写的词考自己，永远绿。

**本次改动**：
- description 压成单行（禁裸换行）+ 规范句式 `触发词：A / B / C`；
- 补业务语言触发词（用户不会说术语，说的是需求），本技能新增词见 SKILL.md「触发词：」段；
- 术语表与业务语言表同步到 `conductor._SKILL_INTENTS` 投影（M-R76 两源一致）。

**配套机制（conductor 侧，一次性全局修）**：
- `_skill_desc_terms` 改为 `finditer` **合并多段** `触发词：`——原 `re.search` 只取第一段，
  第二段业务语言在路由层面根本不存在（「不是没写，是只读了上半句」）；
- 新增**信号源32 投影孤儿词**：查「投影登记了、description 真源没写」。
  `_intents_view()` 做并集派生，孤儿词照样能路由、黄金用例照样绿，
  **所有基于路由的检测都测不出来**——但模型读不到它们，等于"打分器认识、模型不认识"；
- `ROUTE_GOLDEN` 从 20 条扩到 56 条，每个技能 ≥3 条真实业务话术。

**验证**：`ROUTE_GOLDEN` 56/56 命中；双向对账缺口 0/孤儿 0；
`signal-check` 32/32；`verify` 8/9（⑨ 治理刹车属正常劝阻）；
故障注入：删投影→当场红，删真源+投影→黄金用例当场失配（`垃圾清一清` 路由到 None）。

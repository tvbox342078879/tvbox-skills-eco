# 技能自我进化引擎（skill-evolution）

> **定位**：把「规则 48：技能自我进化机制」从纸面变成可执行能力。
> 它不绑定任何业务，是**全局元技能**——监控所有技能/规则的「复发问题」，一旦达标自动立项生成新技能。

## 1. 为什么需要它（规则 48 的核心命题）

技能不是建完就完，而是**活物**。进化的三个来源：

1. **历史任务经验** —— ③ 会话台账（业务经验）+ ④ 资料库经验库（平台经验）
2. **新任务过程** —— 执行中新发现的更短路径 / 可自动化点 / 更优解法
3. **自身判断** —— 对规则合理性、逻辑性、效率的自审（不等新任务触发）

进化的触发（命中即执行，不等人说）：
- 新任务中发现改进方向 → **当场自己改**（更新 SKILL.md / 追加规则 / 补工具）
- 同一问题第 **≥2** 次出现 → 记入 ④ 经验库，标「易复发」
- 同一问题第 **≥3** 次出现（或 ③+④ 合计命中 ≥3）→ **自动立项**：生成独立可升级技能

## 2.4 经验池驱动的技能升级闭环（M-R111 · 1018 立）

> **用户原话**：「技能升级现在只停留在被动升级上……经验池的一个作用就是供技能升级使用，
> 各技能应该在经验池吸收经验来成长；吸收后如有改进计划，咨询我的授权进行升级；
> 还有一个是技能间互相学习的机制也没有。」

**为什么以前没做成**：`lend` 能列出"该技能还没用的招式"，但到此为止——**没人把它变成动作**；
`upgrade` 只改版本号，**不读经验池**；技能之间没有"推送学习"的通道。三个环节各在一处，连不成闭环。

**闭环（四步，缺一不可）**：

```
① absorb   扫招式库未用招式 + recurring 复发聚类 + cross_queue 待推送
      ↓        （数据源：④经验库 138 条 / ③会话台账 99 条 / SEED_MOVES 9 招）
② propose  产出《升级提案清单》：改哪个技能、改什么、依据哪条 ← 只写 upgrade_proposals.json
      ↓
③ 授权闸   用户批准（commit --skill/--all）或驳回（--reject）。**propose 永不改技能**
      ↓
④ commit   升版本 + CHANGELOG 写入"依据 M-R111 提案：…" → **回读闸门** → 提案转 done
```

### ★ 回读闸门（S182 · v1.4.0）：`done` 必须回读得来，不许自称

`commit` **从不修改技能正文**。它只改版本号、写 CHANGELOG、登记 ECO。
所以「升级跑完了」和「招式落进技能了」是两件事，中间必须有一次回读。

标 `done` 之前，用 `SEED_MOVES[tid]['kw']`（招式的**概念关键词**，不是代号）
扫该技能目录下所有 `.py` / `.sh` / `.md`，并按 CHANGELOG 里声明的实现位置核实，给五态：

| 状态 | 判据 | 处理 |
|---|---|---|
| `landed` | ① `.py`/`.sh` 命中 ≥1 个关键词；或 ② CHANGELOG 写 `实现位置 [T-X]` + `证据文件 [T-X]`，且**指针文件真实存在、在生态 skills/ 内** | `done` |
| **`na`** | **文档明确给出结论**（"不适用…" / "这是硬边界" / "已用：…" / "已落地：…"），且结论行**有实质**（反引号路径，或冒号后 ≥8 字说明） | **`done`，完成态** |
| `doc` | 脚本 0 命中、文档在**叙述做法** | `done` + 记 `landed=doc`（**只说不做，必须看得见**） |
| `none` | 只剩清单行/提案回执，或全无 | **退回 `pending`** + 记 `landed_blocked` |
| `unknown` | 目录不存在 / 招式不在 SEED_MOVES | **退回 `pending`**（"查不到"≠"没落地"） |

**`na` 与 `doc` 必须分开。** 「认真评估后判定这招用不上」是**完成**，
「嘴上说要这么做、代码里没做」是**欠账**。混为一谈的后果是逼技能去实现它用不到的招式——
做出来就是纯负担。判定看**行级**：含招式那一行是在讲做法，还是在讲结论。

> 实测教训：29 条里最初报 9 条 `doc`，逐条打开原文后 7 条其实是 `na`。
> 其中 `ecosys-conductor`/T-B 更典型——「搬迁」真的做过（`references/` 下 9 个外置文件），
> 只是发生在文件布局层面，脚本里本就不该有"搬迁"动作。
> **只扫代码的做法，会把"用文件结构体现的落地"当成没做。**

### 实现位置声明（`landed` 的第 ② 条通路）

代码不在本技能目录、或用词与招式完全无关时（跨技能实现、文件布局落地、`.sh` 实现），
在 CHANGELOG 写明：

```markdown
- 实现位置 [T-X]：<一句话说清实现在哪、做了什么>
- 证据文件 [T-X]：`scripts/foo.py`、`/root/.codebuddy/skills/<对岸>/scripts/bar.py`
```

判据会逐个核实指针。**四条硬约束，防止用一段话把欠账洗白：**

1. 指针文件必须**真实存在**，少一个即打回（仍判 `doc`）；
2. 必须在**生态 `skills/` 目录内**，指到 `/tmp` 或外部路径不采信；
3. 光写「已用」「不适用」**不算**，必须有实质内容；
4. 「距结论 2 行内」的豁免也要求对方是**实质结论**，贴空话在真结论旁边不能连带被豁免。

> 为什么不做"内容必须命中关键词"这层校验：实测它把 4 条真落地打回去了
> （`cmd_probe` 全文没有"探针"二字、`link.py` 没写"薄壳"）。
> **要求代码里出现招式术语，等于要求实现者抄招式名字**——这正是判据一直在犯的错。

### `evolve.py patch` — 让它写、让人审（第①档）

为 `doc` 招式生成补丁提案，输出 `upgrade_patches/<技能>__<招式>.md`。

**核心约束：只读技能文件，绝不写入。** 这是"不给它写代码的权限"的具体形式。

- 只处理 `doc`；`na`/`landed`/`none` 不生成
- 候选落点必须**函数体内**命中招式关键词——只名字像的不算
  （第一版按函数名匹配，把查空库的 `_probe_empty_databases` 推荐给「活体探针」，已改）
- 找不到落点时如实说找不到，并列出三种真实可能，**拒绝"为了让判定变绿而硬塞代码"**
- **扫描范围是「全部技能 × 全部招式」，不是提案清单**。这两个集合不一样：
  提案是"某技能没用过某招"，欠账是"文档说了、脚本没做"——任意招式都可能。
  实测：提案清单里 done 的 move 有 29 条，全扫得到的 doc 有 16 格，**两边只交集 2 条**。
  拿一个去推另一个必然漏（S182 实测：第一版只生成 2 份补丁，漏掉 14 份）

```bash
python3 evolve.py patch               # 全部 doc 招式（全量扫描）
python3 evolve.py patch --skill X     # 限定技能
python3 evolve.py patch --no-scan     # 只查提案清单（旧口径，一般不用）
```

**生成不等于该做。** 补丁是"请你判断"，不是"请你去改"。每条先确认是三者中的哪一种：
真欠账（代码里确实没有）／判据误判（做了，但用了别的词）／形式是文件布局（不该按脚本查）。

### `evolve.py apply` — 受控写入（第②档）

**它能改代码了，但只在三把锁同时成立时。**

| 锁 | 内容 | 不过怎么办 |
|---|---|---|
| ① 白名单 | 只改 `<技能>/scripts/*.py`；`SKILL.md`/`CHANGELOG`/数据文件一律拒绝 | 直接拒绝，不动文件 |
| ② 顺序 | `snapshot` → 写入 → 语法检查 → 行为等价 | **自动回滚** |
| ③ 退路 | `apply_guard.py restore <技能>` | 随时可撤，不依赖上次成败 |

```bash
python3 evolve.py apply <技能> <相对路径> "原文本" "新文本"          # 预演，不改文件
python3 evolve.py apply <技能> <相对路径> "原文本" "新文本" --yes     # 真改
python3 apply_guard.py restore <技能>                                # 撤销
```

替换用**文本对**，不用行号（行号会漂）；原文必须**出现且只出现一次**，否则拒绝。

> **行为等价 ≠ 招式落地。** 等价比对只证明"没改坏"，不证明"这招真用上了"。
> 后者只能看 `_move_landed`。两个判据不许互相代替——改完照样是 `doc` 的情况，
> 说明改的地方没用。

**为什么 11 个技能的行为基线能建起来**：全生态只有 2 个技能有自测脚本，
所以"测试先过"多数地方无测试可跑。退一步的硬底线是**只读命令输出改前改后逐字一致**。
入口靠 `ENTRY` 显式登记，**没登记就不跑**——
曾经按"最大的 `__main__` 脚本"猜，猜中 `collect.py` 真去写了生产库。

**判据不许用招式代号，也不许只认自己的黑话。** 正文写的是招式的名字和做法
（「写后回读验证」「移动替代删除」），不是 `T-D`/`T-I`。S181 曾拿代号去搜，得到「全空转」的假结论
——尺子坏了，不是技能空转。

同理：`saved, _ = save_snapshot(...)` + `if not saved: 保留原文件不覆盖` **就是** T-I 的落地形态，
只是它没写"回读验证"四个字。T-I 关键词已补这类同义形态（`saved,` / `不得谎报` / `拒绝覆盖` /
`写失败` / `落盘失败`），补完后 11 条里只有 1 条判定变化，其余无一动。

**★ 判据不许读自己的回执（自证闭环）。** `commit` 会把提案原文
`- 依据 M-R111 提案：吸收通用招式 [T-D] 移动替代删除` 写进 CHANGELOG，
而它**含招式全名**。闸门若把这行当证据，等于「我写下要吸收 → 闸门看到招式名 → 判定已吸收」，
越用越绿。回读前必须先剥掉这类提交痕迹，剥后有命中才算数；剥前有、剥后无，
单独判 `仅命中「提案依据」回执行（自我证明，不算落地）`。

**当前存量（全量 13 技能 × 9 招式 = 117 格，S182 实测）**：

| 态 | 数量 | 说明 |
|---|---|---|
| `landed` | 87 | 脚本命中或指针核实通过 |
| `na` | 30 | 文档明确给出结论（有实质） |
| `doc` | **0** | — |
| `none` | **0** | — |

**117 格全部有了下落**：要么代码在，要么人评估过。没有一格是"既没做也没说"。

> 这轮清账的过程值得留一笔：最初报 16 格 `doc`，逐条核实后发现**没有一条是真欠账**，
> 全是判据认不出实现的真实形态（换语言/换词/换位置/换形式）。修判据之后 `doc` 归零，
> 但同时暴露 `none` 那 10 格——它们不是"判据漏判"，是**从未做过招式评估**
> （automation-task-manager 6 条、learn-hub 3 条、legacy-watchdog 1 条）。
> 补上逐条结论后才归零。`doc` 与 `none` 的区别正在这里：**`doc` 是说了没做，`none` 是连话都没说过。**

**技能间互相学习（cross-learn）**：新招式沉淀后，`cross-learn --move T-X` 自动找出"还没用这招"
的技能，推入 `cross_queue`；下轮 `propose` 变成它们各自的提案，同样等你授权。
（例：清道夫踩到的"`node-info.parentNodeId` 恒为 None"就该推给所有用节点 API 的技能。）

**定时化（关键——治"只被动"）**：挂每日任务跑 `propose`，有提案就摆到你面前等你点头，
没提案不打扰。这样技能是"自己长"的，而不是"你喊它才动"。

```bash
# 建议定时（每日 09:00）：只生成提案，不自动升级
python3 /root/.codebuddy/skills/skill-evolution/scripts/evolve.py propose
```

**安全边界（重要）**：
- `propose` **只读不写**技能文件，产出仅是 JSON 清单；
- `patch` **只读不写**技能文件，只往 `upgrade_patches/` 写补丁提案；
- `commit` 是唯一写入口，且必须带 `--skill`/`--all`（=人工授权信号）；
- 提案可逐条 `--reject`，驳回理由留档，不会被反复提；
- **`commit` 不再是"标 done 就完事"**：没过回读闸门的提案会留在 `pending` 并带 `landed_blocked`，
  下轮还能看见它，不会静默消失。
- **本技能能改技能正文代码了，但只走 `apply` 这一条路**（S182 第②档）。
  `upgrade` 仍只改版本号与 CHANGELOG；`patch` 只出提案；
  真正写代码必须过三把锁：白名单 + 语法/行为等价 + 自动回滚。
  **代码目录之外的任何文件（含 SKILL.md / CHANGELOG）它都改不了。**


## 2.5 用户偏好固化（M-R108 · S154）

> **规则48 的盲区**：过去 recurring 只聚类「问题」（③/④ 里的坑与解法），**不聚类「用户偏好」**。
> 用户反复提的要求（如「会话保持中文」）从不进入 ③/④，于是同一要求提了 ≥3 次仍不被固化，
> 切模型/切会话即回退、反复重提。M-R108 补上这条：用户重复≥3次明确要求 → 立即固化为持久指令。

**机制**：
- 任何用户重复≥3次的要求，即时写入 `ecosys-conductor/scripts/user_standing_instructions.json`（本地持久档；沙箱无法直写③云库时作等价落点，联网后补登 `tvbox log --db TO4LwsjVVdR8JRAUlkejk3`）。
- `evolve.py standing` 列出持久指令清单（重复次数 / 固化状态 / 开工核对 / 云端补登点）——会话开工首步核对并主动声明已生效。

> **S156 补强（M-R108）**：会话开工首步除核对持久指令外，还须**主动触发生态联动**——跑 `tvbox brief`(四极联动速览) 且命中任一技能触发词时必调 `Skill` 工具，使联动设施从「设计存在」变为「每次运行」。治 S148 实证「12884 次调用 Skill 仅 3 次、10 技能全 0 触发」的双向盲区。
- `evolve.py recurring` 输出4 自动带出该清单，使「偏好」与「问题」在同一入口被看见。
- 属主：**skill-evolution** 负责聚类捕获（standing 命令 + recurring 输出4），**ecosys-conductor** 负责规则册（M-R108）与开工核对门禁。

## 3. 「自动创建可升级技能」的硬性要求

生成的技能**必须**满足「可升级」契约，否则视为不达标：

- ✅ 落地后在 ③台账记一条「规则维护」+ ④经验库补一条「建库建夹」

## 4. 周期性系统整理（强制，命中即做）

触发：累计新增 ≥5 条规则 / 距上次整理 >7 天 / 用户要求。

动作（六步，缺一不可）：
1. **去重** —— 重复/重叠规则合并（参考《规则治理总览》主题章）
2. **简化** —— 高效性原则：宁少勿多、宁简勿繁、能合并就合并
3. **强化逻辑** —— 消除矛盾、补齐前提条件
4. **增强合理性** —— 每条规则必须可操作、有判据
5. **复盘** —— 本次改了什么、为什么
6. **技能升级** —— 版本号 + CHANGELOG

## 5. 高效性原则（规则的生命线）

- 一条规则只表达一个可操作判定；含糊、不可执行的规则**不立**
- 能合并就合并，能引用就不重述（数字只存唯一权威源，见规则 47）
- 规则**宁少勿多**：每增加一条先问「能否并入已有规则」
- 历史规则标「已归并」但保留原文，保证可追溯

## 7. 经验对照（规则57 · 招式库 · 方法极联动）

**命题**：技能升级过程中存在大量可相互借鉴处——A 技能的成熟打法（三态契约、SSOT、活体探针…），
B 技能往往也能用上。把这些"跨技能通用招式"抽出来对照，可**显著提速各技能进化**。
此前招式只散落在各技能 CHANGELOG，**无机制记录/检索/回流**（S107 核查结论：确实没做）。

**定位**：生态已有三极联动（数据极 / 技能极 / 用户极），招式库是**第四极·方法极**——
跨技能传递"经验打法"。

### 7.1 招式库（`🥋 通用招式库` `qBQcYoVTqg7v3NAYBa4eSF`）

字段：招式编号(T-A…) / 招式名 / 判据 / 出处技能 / 跨技能数 / 热度(热招≥3/常用2/单点1) / 适用条件 / 时间。

**抽取算法（三层判据 + 防噪）**：
1. **段切分**：只按 `## ` 切段——招式判据只在段内匹配，不跨段串味（抗噪第一道闸）
2. **正则匹配**：`SEED_MOVES` 的判据关键词逐段匹配（**一段可命中多招**——真实 CHANGELOG 常在一段讲多招）
3. **跨技能去重**：判"通用"看**技能数**（set）非出现次数；跨 ≥2 技能才算通用
4. **防噪**：`MOVE_NOISE` 排除元技能自指（skill-evolution 自己讲招式定义）；
   `MOVE_EXCLUDE_RE` 排除 `upgrade` 自动追加的空段
5. **新招式发现** `discover_new_moves`：挖"跨≥2技能但未归类的高频短语" → **只提示不自动入库**

### 7.2 规则57 正文（强规则）

> **规则57｜经验对照**：任何技能升级前，必须先跑 `evolve lend <name> --own` 查有无可借鉴的跨技能通用招式；
> 升级后须把本次新招式回写招式库并登记出处。
>
> **三条判据（可执行）**：
> 1. **升级前必查**：执行 `evolve upgrade <name>` 前，须先跑 `evolve lend <name> --own` 看"未用但适用"清单。
> 2. **升级后必回写**：本次若产生可复用新招式，跑 `evolve mine --skill <name>` 更新出处；
>    若**借鉴了**某招式，须在 CHANGELOG 显式写"借鉴 T-X"；全部不适用须写"不适用 T-X（原因）"。
> 3. **漏项即遗留**：升级了但无对照留痕（既无 lend 记录、CHANGELOG 也无"借鉴/不适用"声明）→
>    由 `review-lend` 报出，conductor 信号源21 扫成遗留项（`未做经验对照`）。
>
> **边界**：① **只诊断不自动改**——mine 产出候选招式交人工确认后入 SEED_MOVES；
> ② 跨≥2技能才叫"通用"，单技能私有打法不入库；
> ③ 借鉴是**建议非强制**，不适用须显式声明（防为凑数硬套，M-R34 双向验证思想）。

### 7.3 与 `evolve upgrade` 的挂钩（软阻断）

- **默认软阻断**：`upgrade` 开头自动跑 `lend --own`，有适用招式则**打印清单提示**，不阻断——
  符合生态门面「旁路、永不阻断主流程」哲学（core.file_to_janitor/register_monitor 同理）。
- **`--strict` 硬阻断**：供 CI/终验用；**`--force`** 确认借鉴后绕过。
- **三态**（M-R57/M-R60）：`lend` 读招式库失败 → 前置检查返回 `None`（无法判定）→ **不阻断、仅告警**，
  绝不折叠成"0 条待借鉴"。
